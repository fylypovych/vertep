# AGENTS-NOGPU.md — реальна перевірка IR Vertep без GPU

## 1. Статус і пріоритет
Це спеціалізована інструкція для уповноваженого стендового виконавця `ir.* NOGPU`. Спершу **прочитати актуальний `AGENTS.md`** і вибрані GitHub Issues. `AGENTS.md` має пріоритет; цей документ не змінює повноважень агента.

## 2. Що означає NOGPU
`NOGPU` **не означає**, що достатньо mock, unit-тестів або ноутбука. IR може вимагати реальний сервер/VM, Docker, systemd, multi-host, PostgreSQL, clean install, live external service, мережу, update/rollback, backup/restore, power-loss чи інші фізичні умови — рівно відповідно до AC.

## 3. Допуск і обмеження
- Перевіряти тільки явно вказані `ir.* NOGPU` або санкціонований власником пакет на конкретному дозволеному стенді.
- Не виконувати GPU-частину змішаного сценарію як NOGPU. Якщо критерій потребує реального GPU, зафіксувати невідповідність класифікації та запросити рішення власника, не змінюючи Issue самостійно.
- Не змінювати production, не виконувати деструктивні операції, reboot, видалення, restore, network isolation, реальні зовнішні публікації чи витратні операції без окремого дозволу та меж тесту.
- Push/release/branches, GitHub issue creation/edit/close заборонені без відповідного окремого доручення; підсумкові коментарі у відповідних NOGPU IR дозволені за розділом «Коментарі в GitHub». Автоматичний режим §4.6–4.7 діє тільки після реальної активації policy gate та незалежної перевірки.

## 4. Інвентаризація
Зафіксувати Git SHA/VERSION, ОС/kernel, VM чи фізичний хост, Docker/Compose, ролі CORE/LAB/Worker, CPU/RAM/disk, IP/мережеву топологію без секретів, стан контейнерів/API/DB, доступ до потрібних зовнішніх систем, ізоляцію та дозволи. Не припускати, що середовище відповідає AC лише тому, що сервіс healthy.

## 5. Цикл для кожного IR
1. Прочитати актуальні Issue body/comments/AC і залежності; звірити фактичний код і конфігурацію.
2. Побудувати `Issue → AC → реальний сценарій → expected → evidence`.
3. Визначити потрібний стенд: single VM, multi-host, clean install, systemd, live API, network failure, update/rollback тощо — без підміни реальних умов симуляцією.
4. Отримати потрібні дозволи, виконати тест на ізольованому стенді, перевірити стан до/після, зберегти мінімальні sanitized докази.
5. Для кожного AC надати `PASS`, `FAIL`, `BLOCKED`. Mock/stub/skip, лише unit/integration тести або успішний health-check не підтверджують реальне IR, якщо AC вимагає іншу межу.
6. Незалежна перевірка доказів обов'язкова там, де її встановлює `AGENTS.md`.

## 6. Типові реальні сценарії (лише за наявності відповідних AC)
- Чиста інсталяція CORE та First Run Wizard; перевірка URL і доступності з клієнтської мережі.
- Docker/systemd startup, restart/recovery, health-check, доступність API та БД.
- Multi-host network, вузли/ролі, автентифікація, таймаути, відновлення з'єднання.
- Update Manager/Agent, rollback, retention, журналювання.
- Backup/restore і fault injection тільки на одноразовому стенді та за прямим дозволом.
- Live external integrations із тестовими credentials і явним дозволом; жодної непогодженої публікації.

## 7. Докази та вердикт
Для кожного AC: номер Issue, точний SHA/VERSION, дата, характеристики стенду, команда/сценарій, expected/actual, exit code, sanitized logs/артефакти, PASS/FAIL/BLOCKED і причина. Фіксувати фактичну перевірку кінцевого результату, а не тільки запуск процесу. Не виводити паролі, токени або персональні дані.

Issue не може бути `completed`, якщо є невиконані обов'язкові AC, `FAIL/BLOCKED` або відсутня необхідна незалежна верифікація. Зміни GitHub і перенесення залишків — лише за умовами `AGENTS.md`.


## Коментарі в GitHub — прямий дозвіл власника
- Власник **прямо дозволив** цьому тестовому агенту писати **коментарі** лише в тих відкритих GitHub Issues типу `ir.* NOGPU`, які входять до явно дорученого набору перевірок. Це окремий дозвіл на коментування відповідно до §4.4 `AGENTS.md`, **не** дозвіл на інші зміни GitHub.
- Після завершення перевірки конкретного Issue (включно з частковим результатом або блокуванням) опублікувати **один стислий підсумковий коментар** українською: Git SHA/VERSION, стенд і дата, кожен AC та PASS/FAIL/BLOCKED, фактичні докази/команди або посилання на безпечні артефакти, причини FAIL/BLOCKED, результат незалежної верифікації (якщо є). Не писати PASS без доказів.
- Якщо з'явилися нові істотні результати, дозволений наступний коментар із чітким позначенням повторної перевірки; не дублювати незмінні звіти. Перед записом перевірити номер, тип, scope та відсутність уже опублікованого ідентичного підсумку.
- Не публікувати секрети, токени, приватні адреси, персональні дані, повні дампи або небезпечні команди з credentials. Не змінювати назву, body, labels, assignees, статус чи Project fields; не створювати/закривати/переносити Issues, PR, branches, commits або releases на підставі цього дозволу.
- Якщо `AGENTS.md` вимагає незалежної перевірки чи policy gate для **закриття** IR, коментар може повідомити про відсутність такого підтвердження, але не замінює його. Автоматичне закриття можливе лише за окремо чинними умовами §4.6–4.7.

## 8. Приклад стартового доручення Codex CLI
> Прочитай AGENTS.md і AGENTS-NOGPU.md. Перевір тільки IR #<номер> на цьому дозволеному NOGPU-стенді. Спочатку визнач реальні вимоги до середовища і безпеку. Без push, release, створення/закриття/редагування Issues, видалення, reboot чи деструктивних тестів без окремого дозволу. Публікуй підсумковий коментар лише в перевірюваному NOGPU IR. Для кожного AC надай PASS/FAIL/BLOCKED та відтворювані докази.
