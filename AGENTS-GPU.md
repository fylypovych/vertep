# AGENTS-GPU.md — реальна перевірка GPU-залежних IR Vertep

## 1. Статус і пріоритет
Цей документ є спеціалізованою інструкцією для уповноваженого стендового виконавця GPU IR. Перед роботою **обов'язково прочитати актуальний `AGENTS.md` репозиторію** та відповідні GitHub Issues. Якщо правила суперечать одне одному, переважає `AGENTS.md` і прямі обмеження власника. Цей файл не надає додаткових прав.

## 2. Допуск до тестів
- Працювати лише з конкретними `ir.* GPU` Issues або явно санкціонованим власником набором і на вказаному тестовому сервері. Не запускати весь backlog за власною ініціативою.
- З'ясувати: чи сервер орендований/одноразовий, чи містить чужі дані, чи дозволені GPU-навантаження, restart, зміни Docker/systemd, доступ до зовнішніх API, витрати, мережеві тести.
- За замовчуванням — read-only аудит і безпечні недеструктивні перевірки. Деструктивні тести, видалення, перезапуск продуктивних компонентів, stress/24×7, restore/rollback, зміна драйверів, production-доступ — лише в межах явного дозволу.
- Не виконувати push/release, не створювати гілок або Issues, не змінювати статусів GitHub без належного окремого доручення. Коментарі до відповідних IR дозволені за правилами розділу «Коментарі в GitHub». Спеціальний автоматичний режим §4.6–4.7 `AGENTS.md` застосовується лише після фактичної активації policy gate та незалежної верифікації.

## 3. Передстартова інвентаризація
Зафіксувати (без секретів): Git SHA і Vertep VERSION, назву/тип хоста, Ubuntu/kernel, Docker/Compose, GPU модель/VRAM, NVIDIA driver/CUDA runtime, `nvidia-smi`, видимість GPU всередині потрібних контейнерів, доступні CPU/RAM/disk, мережеву топологію, роль вузла, ізоляцію від production.

## 4. Цикл для кожного IR
1. Отримати точний опис, коментарі, залежності та AC Issue з GitHub; звірити поточний код/конфігурацію і чинні тести.
2. Побудувати таблицю `Issue → AC → test case → expected → evidence` без додавання нових AC.
3. Перед кожним тестом визначити безпечні межі та необхідні дозволи; перевірити наявність реального GPU, а не mock або CPU fallback.
4. Виконати реальний сценарій на дозволеному стенді: GPU inference, GPU Worker/queue, VRAM allocation/release, lease/revoke, parity, end-to-end — **тільки якщо це прямо входить до AC**. Перевірити результат та стан після тесту, включно з логами й cleanup без втрати чужих даних.
5. Для кожного AC поставити `PASS`, `FAIL` або `BLOCKED`. `SKIP`, mock, unit-тест, контейнер у стані running чи сам факт доступності `nvidia-smi` не є доказом проходження реального IR.
6. Незалежний Verification Agent має підтвердити докази там, де цього вимагає `AGENTS.md`. Не вважати самоперевірку незалежною.

## 5. Мінімум доказів
- Issue, AC, точний Git SHA/VERSION, дата/час, сервер і конфігурація, команда або відтворюваний сценарій.
- Expected/actual/verdict, exit code, релевантні sanitized logs, метрики GPU/VRAM, ID завдання, часові межі, результат API/контейнера, перевірка звільнення ресурсів — залежно від AC.
- Чітко відокремити підтверджені факти від припущень. Не завантажувати секрети, токени, персональні дані або повні дампи середовища до GitHub.
- Повторні тести не стирають історію невдач: вказати повторну спробу та причину.

## 6. Рішення і звіт
- `PASS`: усі умови конкретного AC доведено на потрібному фізичному GPU.
- `FAIL`: виконаний дозволений тест показав невідповідність.
- `BLOCKED`: бракує дозволу, обладнання, доступу, залежності або іншої конкретної умови.
- Issue загалом не може бути `completed`, якщо хоча б один обов'язковий AC має `FAIL/BLOCKED` або відсутня необхідна незалежна верифікація.
- Звіт українською: `Issue | AC | середовище/SHA | тест | expected | actual | evidence | verdict | blocker/next action`.
- Не закривати/переносити Issue без умов §4.7 `AGENTS.md` або окремого доручення. Не створювати дубльовані IR; залишки класифікувати за існуючими AC.


## Коментарі в GitHub — прямий дозвіл власника
- Власник **прямо дозволив** цьому тестовому агенту писати **коментарі** лише в тих відкритих GitHub Issues типу `ir.* GPU`, які входять до явно дорученого набору перевірок. Це окремий дозвіл на коментування відповідно до §4.4 `AGENTS.md`, **не** дозвіл на інші зміни GitHub.
- Після завершення перевірки конкретного Issue (включно з частковим результатом або блокуванням) опублікувати **один стислий підсумковий коментар** українською: Git SHA/VERSION, стенд і дата, кожен AC та PASS/FAIL/BLOCKED, фактичні докази/команди або посилання на безпечні артефакти, причини FAIL/BLOCKED, результат незалежної верифікації (якщо є). Не писати PASS без доказів.
- Якщо з'явилися нові істотні результати, дозволений наступний коментар із чітким позначенням повторної перевірки; не дублювати незмінні звіти. Перед записом перевірити номер, тип, scope та відсутність уже опублікованого ідентичного підсумку.
- Не публікувати секрети, токени, приватні адреси, персональні дані, повні дампи або небезпечні команди з credentials. Не змінювати назву, body, labels, assignees, статус чи Project fields; не створювати/закривати/переносити Issues, PR, branches, commits або releases на підставі цього дозволу.
- Якщо `AGENTS.md` вимагає незалежної перевірки чи policy gate для **закриття** IR, коментар може повідомити про відсутність такого підтвердження, але не замінює його. Автоматичне закриття можливе лише за окремо чинними умовами §4.6–4.7.

## 7. Приклад стартового доручення Codex CLI
> Прочитай AGENTS.md і AGENTS-GPU.md. Перевір тільки IR #<номер> на цьому дозволеному GPU-стенді. Спочатку інвентаризація та оцінка безпеки. Без push, release, створення/закриття Issues, видалення чи деструктивних операцій. Публікуй підсумковий коментар лише в перевірюваному GPU IR. Для кожного AC надай PASS/FAIL/BLOCKED і відтворювані докази. Якщо потрібні додаткові дозволи — зупини відповідний тест і запитай.
