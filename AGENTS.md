# Vertep — правила для агентів

## 1. Місія проєкту

Vertep — оркестратор автоматизованої фабрики короткого медіаконтенту з віртуальними персонажами.  
Vertep **не генерує контент** — він керує інструментами, які генерують контент.  
Це мозок, диспетчер і оркестратор системи. Інструменти: Ollama, ComfyUI, FFmpeg, TTS, Publisher-модулі.

Ключовий принцип:  
> Вертеп — це конвеєр. Моделі змінюються. GPU змінюються. Workflow змінюються. Персонажі додаються й закриваються. А Vertep залишається центральною системою.

---

## 2. Мова

- Користувацькі описи, коміти, нотатки релізів, UI — **українською**.
- Технічні терміни — англійською: API, Docker, PostgreSQL, Redis, ComfyUI, FFmpeg, Ollama, job, scene, task, workflow, worker, CORE, GPU Node, Text Node, Voice Node, Publisher Node, Backup Node, Monitoring Node.

## 3. Версіонування та релізи

### 3.1 Нумерація

- Формат: `0.0.0.X` — послідовна нумерація.
- Кожен новий коміт у `main` отримує наступний послідовний номер.
- Перед вибором номера перевірити історію комітів і наявність тегів у репозиторії.
- Перевірити локальні теги:
  `git tag --list | Select-String "0\.0\.0\."`
- Перевірити remote-теги:
  `git ls-remote origin --tags | Select-String "0\.0\.0\."`
- Якщо номер уже використаний — не перезаписувати історію, а вибрати наступний вільний послідовний номер.
- Не допускати повторного використання одного номера для різних нових комітів.
- Нова нумерація повинна продовжувати правильну послідовність незалежно від помилок у назвах старих комітів.

### 3.2 Один реліз — один коміт

- Заборонено створювати окремий технічний коміт з кодом, а потім окремий коміт від release-бота.
- Той самий релізний коміт містить:
  - усі зміни коду;
  - новий `VERSION`;
  - `CHANGELOG.md`;
  - `releases/<версія>.md`;
  - оновлені тести;
  - оновлену документацію.
- Release-бот не повинен створювати додатковий коміт після релізного коміту.

### 3.3 Назва нового коміту

Назва нового релізного коміту:

`<версія>`

Приклад:

`0.0.0.89`

Для нових комітів не додавати опис після номера версії в назві коміту.

Детальний опис змін зберігається в:

- `CHANGELOG.md`;
- `releases/<версія>.md`;
- GitHub Release.

### 3.4 Перед створенням релізу

Перед створенням релізного коміту обов'язково:

- Додати українські пункти змін до секції `Unreleased` у `CHANGELOG.md`.
- Виконати повний набір тестів:
  `python -m pytest -q`
- Перевірити:
  `git diff --check`
- Переконатися, що в змінах немає секретів, паролів, токенів, API-ключів, приватних ключів та інших конфіденційних даних.
- Переконатися, що номер нової версії ще не використаний.
- Переконатися, що всі файли, які повинні входити до релізу, включені до майбутнього релізного коміту.

### 3.5 Створення релізу

- Всі зміни мають бути закомічені в один релізний коміт з назвою `<версія>`.
- Після створення коміту запустити:

`python scripts/release.py --title "<версія>: <опис українською>"`

- `release.py` повинен:
  - перевірити версію;
  - створити необхідний тег;
  - запушити релізний коміт;
  - запушити тег;
  - створити GitHub Release;
  - тригернути GitHub Actions workflow.
- Для нових релізів заборонено переміщувати або перезаписувати вже існуючий тег іншого релізу.

### 3.6 Після створення

Після створення релізу виконати:

`python scripts/release.py --check`

Перевірка повинна підтвердити коректність релізу, тегів, GitHub Release та необхідних артефактів.

### 3.7 Runtime bundle

- Кожен реліз **обов'язково** має містити артефакт:
  `vertep-runtime-<версія>.tar.gz`
- GitHub Actions workflow збирає runtime bundle, прикріпляє його до GitHub Release і публікує версійний тег.
- Якщо workflow не створила артефакт — реліз вважається невалідним.
- Bootstrap не повинен встановлювати реліз без валідного runtime bundle.
- Не вважати release завершеним, якщо артефакт `vertep-runtime-<версія>.tar.gz` відсутній.
- **Обов'язково**: у GitHub Repository Secrets має бути `RUNTIME_SIGNING_PRIVATE_KEY` для підпису runtime bundle.

### 3.8 Перед push

Перед push перевірити:

- Назва коміту відповідає формату `<версія>`.
- `VERSION` містить ту саму версію.
- `CHANGELOG.md` має секцію з цією версією.
- `releases/<версія>.md` існує.
- Всі необхідні зміни включені до релізного коміту.
- `git status` чистий.
- Локальний SHA релізного коміту визначений і не змінюється під час release-процесу.

### 3.9 Push

- `release.py` робить push автоматично.
- Заборонено ручний push до `main` після створення релізу.
- Заборонено створювати додаткові технічні коміти між релізним комітом і його тегом.
- SHA тега релізу повинен відповідати SHA релізного коміту.

### 3.10 GitHub Actions

GitHub Actions:

- перевіряє релізний коміт;
- **обов'язково** збирає runtime bundle `vertep-runtime-<версія>.tar.gz`;
- runtime bundle повинен містити всі необхідні runtime-файли, зокрема:
  - `docker-compose.yml`;
  - `docker-compose.amd.yml`;
  - `docker-compose.nvidia.yml`;
  - `manifest.json` з цифровим підписом;
  - `node_roles.json`;
  - `deployment-plan.py`;
  - `update-agent.py`;
  - `vertep` CLI;
  - SBOM файл;
  - systemd unit файли;
  - конфіги моніторингу;
- створює signed manifest з SHA256 для кожного файла;
- прикріпляє runtime bundle до GitHub Release;
- публікує версійний тег і `latest`.

**Заборонено для бота:**

- змінювати `VERSION`;
- змінювати `CHANGELOG.md`;
- створювати додатковий коміт;
- виконувати push нового коміту в `main`;
- генерувати англомовний опис релізу замість українського;
- змінювати SHA релізного коміту.

### 3.11 Після workflow

Після завершення workflow обов'язково перевірити:

- У GitHub Release є артефакт:
  `vertep-runtime-<версія>.tar.gz`
- SHA `origin/main` і SHA тега релізу збігаються.
- Тег вказує саме на релізний коміт.
- Після релізного коміту не з'явився додатковий коміт від бота.
- Runtime bundle відповідає версії релізу.
- Workflow завершився без помилок.

### 3.12 Docker-образи

- Кожен реліз збирає всі Docker-образи з того самого SHA.
- Тег кожного образу точно збігається з `VERSION`.
- Заборонено:
  - використовувати образи від іншої версії;
  - вручну перезаписувати версійний тег;
  - публікувати реліз, якщо хоча б один обов'язковий образ не зібрався;
  - використовувати лише `latest` як джерело версії.
- Workflow:
  - збирає образи;
  - публікує версійний тег;
  - публікує `latest`;
  - записує digest кожного образу в підписаний маніфест.
- Встановлення використовує immutable digest, а не `latest`.

### 3.13 Перевірка перед релізом

Перед кожним новим релізом:

- Виконати:
  `git tag --list | Select-String "0\.0\.0\."`
- Переконатися, що локальний тег нової версії ще не існує.
- Виконати:
  `git ls-remote origin --tags | Select-String "<версія>"`
- Переконатися, що тег не існує на remote.
- Перевірити історію комітів і визначити наступний правильний послідовний номер.
- Якщо номер уже використаний — не перезаписувати історію і не використовувати його повторно.
- Вибрати наступний правильний номер.

### 3.14 Нормалізація історії комітів

Під час аналізу, документування або відновлення історії репозиторію кожному коміту визначається правильний послідовний номер у форматі:

`0.0.0.X`

Правильний номер визначається за фактичною послідовністю комітів у `main`.

**Кожен коміт у послідовності враховується**, навіть якщо:

- він не має номера версії в оригінальній назві;
- був створений агентом або ботом;
- має технічну назву;
- містить неправильний номер;
- дублює номер іншого коміту;
- номер у назві був пропущений.

Нормалізація використовується для правильного представлення історії.

**Існуючу Git-історію заради нормалізації не переписувати.**

### 3.15 Формат правильно названого історичного коміту

Якщо номер в оригінальній назві коміту відповідає його правильному послідовному номеру, використовувати формат:

## ПРАВИЛЬНА НАЗВА: <версія>

- <зміна 1>
- <зміна 2>
- <зміна 3>

Приклад:

## ПРАВИЛЬНА НАЗВА: 0.0.0.88

- Додано `AGENTS.md` — єдине правило для агентів проєкту: мова, версіонування, архітектура, сценарний агент, ComfyUI executor, FFmpeg пайплайн, Bootstrap/First Run Wizard, Safe Update System, тестування, безпека.
- Реалізовано ComfyUI executor у `worker/role_executor.py`: додано `execute_image()`/`execute_video()`, зареєстровано в `EXECUTORS`/`ROLE_TASKS`.
- Уніфіковано `worker/service.py`: тепер всі задачі викликаються через `execute_role_task()`, включаючи `image`/`video`.
- Створено `core/script_agent.py` — багатоступінчастий сценарний агент: структура → плани сцен → деталізація кожної сцени.
- Оновлено `core/pipeline.py`: переведено на `ScriptAgent`, передача конфігу персонажа, fallback на перегенерацію окремої сцени.
- Оновлено `tests/test_features.py`: замінено `LLMAdapter` на `ScriptAgent` у monkeypatch.

У цьому випадку рядок `ОРИГІНАЛЬНА НАЗВА` не виводити.

### 3.16 Формат неправильно названого історичного коміту

Якщо номер або назва існуючого коміту не відповідає його правильному послідовному номеру, використовувати формат:

## ПРАВИЛЬНА НАЗВА: <правильний послідовний номер>

## ОРИГІНАЛЬНА НАЗВА: <оригінальна назва коміту без змін>

- <зміна 1>
- <зміна 2>
- <зміна 3>

Приклад:

## ПРАВИЛЬНА НАЗВА: 0.0.0.85

## ОРИГІНАЛЬНА НАЗВА: 0.0.0.84 — Виправлення Telegram polling та publisher-worker

- Переведено Telegram-інтеграцію з webhook на long polling.
- Виправлено роботу `publisher-worker`.
- Додано обробку `PermissionError` у health check.

`ОРИГІНАЛЬНА НАЗВА` повинна бути скопійована з Git без виправлень, перекладу або нормалізації.

### 3.17 Коміт без номера версії

Якщо історичний коміт взагалі не має номера `0.0.0.X`, він все одно отримує правильний номер відповідно до своєї позиції в історії.

Формат:

## ПРАВИЛЬНА НАЗВА: <правильний послідовний номер>

## ОРИГІНАЛЬНА НАЗВА: <оригінальна назва коміту>

- <фактичні зміни коміту>

Приклад:

## ПРАВИЛЬНА НАЗВА: 0.0.0.79

## ОРИГІНАЛЬНА НАЗВА: Migrate Telegram integration from webhook to long polling

- Переведено Telegram-інтеграцію з webhook на long polling.
- Оновлено відповідні конфігурації та обробку Telegram-повідомлень.

Такий коміт є повноцінною одиницею послідовної історичної нумерації.

### 3.18 Правила формування опису історичного коміту

Опис під `ПРАВИЛЬНА НАЗВА` формується на основі фактичного вмісту відповідного коміту.

Для визначення змін використовувати:

- `git show`;
- diff відповідного коміту;
- список змінених файлів;
- фактичні зміни функцій, класів, конфігів, тестів і документації.

Правила опису:

- Писати українською мовою.
- Використовувати маркований список.
- Описувати фактично реалізовані зміни.
- Не покладатися лише на оригінальну назву коміту.
- Не вигадувати зміни, яких немає у diff.
- Назви файлів, директорій, функцій, класів, команд, параметрів та інших технічних сутностей оформлювати в `code`.
- Об'єднувати дрібні технічні зміни в логічні пункти, якщо це не спотворює зміст.
- Не приховувати суттєві зміни лише тому, що вони не згадані в оригінальній назві коміту.

### 3.19 Правила визначення правильної історичної нумерації

- Правильна нумерація визначається за фактичною послідовністю комітів у `main`.
- Кожен коміт враховується один раз.
- Нумерація є безперервною.
- Не пропускати коміт через відсутність версії в його назві.
- Не пропускати коміт через те, що він був створений агентом, ботом або автоматизацією.
- Не присвоювати двом різним комітам одну `ПРАВИЛЬНУ НАЗВУ`.
- Помилкова оригінальна версія не впливає на подальший підрахунок правильної послідовності.
- `ПРАВИЛЬНА НАЗВА` є нормалізованим представленням коміту, а не зміною його Git metadata.
- `ОРИГІНАЛЬНА НАЗВА` завжди зберігає фактичний Git subject коміту.

### 3.20 Заборона переписування історії

Для виправлення історичної нумерації **заборонено**:

- `git rebase` для перейменування старих комітів;
- `git commit --amend` старих комітів;
- `git reset` з метою перебудови опублікованої історії;
- `git push --force`;
- `git push --force-with-lease` для нормалізації назв;
- змінювати SHA існуючих опублікованих комітів;
- переміщувати існуючі теги заради виправлення старої нумерації;
- видаляти історичні коміти лише через неправильну назву;
- об'єднувати старі коміти лише для приведення нумерації до правильної.

Нормалізація історії змінює **лише її документальне представлення**.

Існуючі:

- SHA комітів;
- Git subjects;
- теги;
- GitHub Releases;
- порядок комітів

залишаються незмінними.

### 3.21 Нова нумерація після виявлення історичних помилок

Якщо під час аналізу виявлено, що стара видима нумерація `0.0.0.X` розійшлася з реальною кількістю та послідовністю комітів:

1. Визначити правильний номер кожного історичного коміту.
2. Зафіксувати розбіжності через `ПРАВИЛЬНА НАЗВА` та, за потреби, `ОРИГІНАЛЬНА НАЗВА`.
3. Не переписувати існуючу Git-історію.
4. Визначити правильний номер останнього коміту.
5. Наступний новий релізний коміт отримує наступний номер після **правильного номера останнього коміту**, а не сліпо наступний номер після останньої оригінальної назви.
6. Перед використанням нового номера додатково перевірити, що відповідний Git tag не зайнятий.
7. Якщо правильний наступний номер конфліктує з уже існуючим історичним тегом, не перезаписувати тег; вибрати наступний безпечний номер і задокументувати розбіжність.


### 3.22 Форматування історії без порожніх рядків

Під час формування нормалізованої історії комітів **заборонено вставляти порожній рядок між заголовком коміту та його описом**.

Правильний формат:

## ПРАВИЛЬНА НАЗВА: 0.0.0.89
- <зміна 1>
- <зміна 2>
- <зміна 3>

Якщо присутня оригінальна назва:

## ПРАВИЛЬНА НАЗВА: 0.0.0.85
## ОРИГІНАЛЬНА НАЗВА: 0.0.0.84 — Виправлення Telegram polling та publisher-worker
- <зміна 1>
- <зміна 2>
- <зміна 3>

Правила форматування:

- Після `## ПРАВИЛЬНА НАЗВА: ...` не вставляти порожній рядок.
- Між `ПРАВИЛЬНА НАЗВА` та `ОРИГІНАЛЬНА НАЗВА` не вставляти порожній рядок.
- Після `## ОРИГІНАЛЬНА НАЗВА: ...` не вставляти порожній рядок.
- Опис починається безпосередньо з наступного рядка після останнього заголовка.
- Кожен пункт опису починається з нового рядка через `- `.
- Між пунктами опису порожні рядки не вставляти.
- **Порожній рядок дозволений тільки перед початком наступного коміту**, тобто перед наступним `## ПРАВИЛЬНА НАЗВА: ...`.
- Не використовувати додаткові абзаци всередині опису одного коміту.

Так. Тут варто зафіксувати **єдиний формат `releases/<версія>.md`**, щоб агент більше не вигадував `# Реліз ...`, `# Release ...` тощо. Додай до `AGENTS.md` після правил релізу: 

### 3.24 Формат файла нотаток релізу

Для кожного нового релізу обов'язково створюється файл:

`releases/<версія>.md`

Приклад:

`releases/0.0.0.92.md`

Файл повинен починатися строго із заголовка:

`# Vertep <версія>`

Приклад:

`# Vertep 0.0.0.92`

Правила:

- Назва файла повинна точно відповідати значенню `VERSION`.
- Версія в заголовку повинна точно відповідати значенню `VERSION`.
- Перший рядок файла повинен мати формат `# Vertep <версія>`.
- Не використовувати альтернативні заголовки:
  - `# Реліз <версія>`;
  - `# Release <версія>`;
  - `# Vertep Release <версія>`;
  - інші варіанти.
- Після заголовка розміщується український опис фактичних змін релізу.
- Нотатки релізу повинні відповідати змінам у `CHANGELOG.md`.
- `scripts/release.py --check` повинен перевіряти наявність файла та точну відповідність його заголовка формату `# Vertep <VERSION>`.
- Агент не повинен змінювати або послаблювати цю перевірку для обходу помилки у файлі нотаток релізу.
- Якщо перевірка повідомляє `Файл нотаток релізу містить неправильну версію`, спочатку перевірити `releases/<VERSION>.md`, його назву та перший рядок.

Це прямо закриває ситуацію, яка сталася з `0.0.0.92`.

## 4. Архітектурні принципи

### 4.1 CORE не генерує контент
- Всі генерації (текст, зображення, відео, голос) виконуються worker-ами через адаптери.
- CORE лише диспетчеризує задачі (`task`) і збирає артефакти.

### 4.2 Персонажі — конфіги, не код
- Нові персонажі додаються через `/characters/<id>/` директорію.
- Кожен має: `character.json`, `system_prompt.txt`, `voice.json`, `visual.json`, `generation.json`, `publishing.json`.
- Не додавати персонажів у хардкод.

### 4.3 Workflow — окремо від коду
- ComfyUI workflow зберігаються в `/workflows/`.
- CORE лише передає шлях workflow в задачі.
- Зміна моделі/LoRA/sampler не потребує зміни коду CORE.

### 4.4 Publisher — модульний
- Кожна платформа (YouTube, TikTok, Facebook, Instagram, Threads) — окремий адаптер.
- CORE передає готовий ролик і метадані, Publisher виконує публікацію.

### 4.5 Web UI
- Локалізація: українська (`admin-uk.js`, `admin-uk.css`).
- Дії: Pause / Resume / Retry / Regenerate / Cancel / Delete / Approve / Publish.

### 4.6 Інсталяція — Deployment Wizard
- Один bootstrap.sh на чисту Ubuntu 24.04.
- Користувач вибирає роль вузла: Core / GPU / Text / Voice / Publisher / Backup / Monitoring.
- Кожна роль встановлює лише необхідні компоненти.
- Після bootstrap — First Run Wizard через Web UI.
- Після завершення — користувач працює виключно через Web UI (Zero Shell).
- Всі сервіси — у Docker контейнерах, volumes для даних.
- Секрети генеруються автоматично, зберігаються у внутрішньому сховищі.

### 4.7 Immutable Runtime
- Користувач не змінює контейнер вручну.
- Будь-які зміни — через Web UI або офіційні оновлення.
- Якщо контейнер пошкоджено — замінюються новим образом.
- Усі дані, конфігурація, БД — у volumes.

Перше джерело — Telegram. Подальші (RSS, сайти, API, ручне створення, тренди) додавати як модулі, не змінюючи ядро.

## 7. Ролі вузлів

- `core` — CORE + API + Dispatcher + Scheduler + Publisher + Redis + PostgreSQL + License Manager + Update Agent + Monitoring.
- `gpu` — Worker + ComfyUI + CUDA Runtime + Update Agent.
- `text` — Worker + Ollama + LLM Runtime + Update Agent.
- `voice` — Worker + TTS Runtime + Voice Models + Update Agent.
- `publisher` — Publisher Worker + платформи + Update Agent.
- `backup` — Backup Service + Snapshot Manager + Archive Service + Update Agent.
- `monitoring` — Grafana + Prometheus + Logs + Metrics + Update Agent.

Додаткові ролі активуються через `NODE_ADDITIONAL_ROLES` у `.env`.

---

## 8. Capability-driven архітектура

- Роль визначає, що встановити.
- Capabilities визначають, що вузол реально може виконувати.
- Dispatcher шукає вузол за потрібною capability, а не за роллю.
- Приклад capabilities: `image_generation`, `image_upscale`, `controlnet`, `inpainting`, `video_generation`, `tts`, `publish_youtube`, `publish_tiktok`.
- Worker сам повідомляє Core свої capabilities при реєстрації.

---

## 9. Відмовостійкість

- `recover_after_restart()` відновлює Job після перезавантаження CORE.
- Worker надсилають heartbeat.
- Після reboot основні компоненти запускаються автоматично через systemd.
- Startup recovery service відновлює стан системи.

---

## 10. Глобальні стани системи

```
NORMAL — штатна робота.
MAINTENANCE — нові задачі лише накопичуються.
UPDATING — жодні задачі не запускаються.
RECOVERING — відновлення після невдалого оновлення.
READ_ONLY — тільки читання.
EMERGENCY — лише аварійні дії адміністратора.
```

Усі модулі орієнтуються на глобальний стан через `get_system_state()`.

## 11. Safe Update System

### 11.1 Джерело оновлень
- Оновлення отримуються виключно з `https://update.vertep.ai` (або вказаного `VERTEP_UPDATE_SERVER`).
- GitHub використовується лише командою розробки.

### 11.2 Запуск оновлення
- Автоматично: періодична перевірка (раз на 6 годин через systemd timer).
- Через Web UI: Settings → Update → Install.
- Через CLI: `vertep update`.

### 11.3 Перехід у Maintenance
- Перед оновленням система переходить у `MAINTENANCE`.
- Dispatcher перестає видавати нові задачі.
- Активні задачі продовжують виконуватися.
- Нові задачі отримують `WAITING_FOR_SYSTEM`.

### 11.4 Drain Mode
- Dispatcher переходить у `DRAIN`.
- Нові задачі не запускаються.
- Worker завершують поточну роботу і повідомляють Core: `FREE`.

### 11.5 Backup перед оновленням
- Автоматично створюється резервна копія: конфігурація, PostgreSQL, Redis, локальні налаштування, ліцензії, секрети, журнали міграцій.
- Зберігається у `/opt/vertep/backups/update-<stamp>/`.

### 11.6 Оновлення
- Завантажуються нові контейнери.
- Виконується міграція БД.
- Перезапускаються сервіси.

### 11.7 Health Check після оновлення
- Перевірка: PostgreSQL, Redis, API, Web UI, Ollama, Dispatcher, GPU, Driver, CUDA, ComfyUI, VRAM.
- Кожен Worker проходить самотестування (мінімальний workflow).
- Лише після успішного завершення: `STATUS = READY`.

### 11.8 Rollback
- Якщо будь-який Health Check завершився помилкою — оновлення скасовується.
- Автоматично виконується: відновлення попередньої версії, контейнерів, БД, запуск попередньої конфігурації.
- `vertep rollback` — ручний rollback через CLI.

### 11.9 Rolling Update
- Оновлює вузли по одному (one-node-at-a-time).
- Canary promotion: перший вузол оновлюється, проходить self-test, потім підтверджується (promote) або відкочується (rollback).
- Підтримка порядків: `workers-first`, `core-first`, `custom`.
- Автоматичний rollback при таймауті або помилці.

### 11.10 Логування
- Окремий журнал оновлень: `/data/config/update/status.json`, `/data/config/update/log/`.
- Кожен запис: час, фаза, статус, повідомлення.

## 13. First Run Wizard

### 13.1 Кроки
1. **Роль вузла** — вибір зі списку. Для non-Core: введення Core URL, Core Certificate, Registration Token.
2. **Назва інсталяції** — ім'я системи, домен (необов'язково).

8. **Installation Manifest** — перегляд, можливість завантажити JSON.
9. **Готово** — Installation ID, Core URL, Core Certificate, Registration Token.

### 13.2 Core Wizard
- Генерує перший Registration Token для підключення Worker-ів.
- Відображає Core Certificate для імпорту на Worker-и.

### 13.3 Non-Core Wizard
- Вводить Core URL, Core Certificate, Registration Token.
- Отримує JWT, Worker Secret, Configuration.
- Реєструється у Core через `/api/nodes/register`.

## 14. Registration Token

- Генерується Core для підключення Worker-ів.
- Формат: `VT-XXXX-XXXX-XXXX` (32 hex символи).
- TTL: 15 хвилин (за замовчуванням).
- Зберігається в базі даних (`node_registration_tokens`).
- Використовується один раз, потім видаляється.

---

## 15. Node Registry

- Core веде реєстр усіх вузлів.
- Кожен вузол має: `node_id`, `role`, `capabilities`, `hardware`, `version`, `status`, `last_heartbeat`.
- Worker надсилає heartbeat кожні 30 секунд.
- Core автоматично визначає `ONLINE / BUSY / FREE / UPDATING / OFFLINE / ERROR`.

---

## 16. Worker Registration Flow

1. Bootstrap встановлює роль, генерує CSR.
2. Користувач вводить Core URL + Registration Token у Wizard.
3. Worker відправляє `/api/nodes/register` з CSR, capabilities, hardware.
4. Core перевіряє токен, видає JWT + Worker Secret + Configuration.
5. Worker зберігає credentials, запускає сервіси.
6. Worker з'являється у Web UI Core.

---

## 17. GPU Dispatcher

- CORE постійно знає стан усіх WORKER.
- При створенні GPU-задачі вказуються вимоги: `IMAGE / MIN_VRAM 6 GB` або `VIDEO / MIN_VRAM 20 GB`.
- Dispatcher сам визначає, на яку машину відправити задачу.
- Підтримує різні GPU: NVIDIA, AMD.
- Worker сам повідомляє свої capabilities при реєстрації.

## 18. Сценарний агент

- Генерація сценарію — багатоступінчаста:
  1. **Structure**: заголовок, опис, хештеги, план сцен.
  2. **Scenes**: для кожної сцени окремий LLM-виклик з промптом персонажа + сценарію.
  3. **Assembly**: збір фінального script, нормалізація через `ScriptDocument`.
- Реалізація: `core/script_agent.py`.
- Виклик: `ScriptAgent().generate_script()` в `core/pipeline.py:prepare_job()`.
- Fallback: якщо сцена невалідна — перегенерувати лише її, не весь сценарій.
- Персонаж передається як конфіг, не хардкод.

## 19. ComfyUI Executor

- Додавати в `worker/role_executor.py` як `execute_image()`/`execute_video()`.
- Реєструвати в `EXECUTORS`/`ROLE_TASKS`.
- Не викликати `ComfyUIAdapter` напряму в `worker/service.py` — використовувати `execute_role_task()`.
- Fallback для відео: якщо ComfyUI не повернув відео — зібрати з кадрів через FFmpeg.

## 20. FFmpeg пайплайн

- Збірка виконується через `FFmpegAdapter` в `core/pipeline.py:finalize_job()`.
- Не переносити на worker без явного завдання.
- Підтримує: відеоряд, pan/zoom, переходи, голос, музика, субтитри, заставки, фінальне кодування.
- Принцип: не витрачати GPU на те, що нормально робиться звичайним монтажем.

---

## 21. Тестування

- Перед кожним релізом: `python -m pytest -q`.
- Допустимі невдачі: тільки e2e через `ERR_CONNECTION_REFUSED 127.0.0.1:8080` (браузерні тести без запущеного сервера).
- Будь-які нові падіння в `tests/test_features.py` або інших модульних тестах — блокують реліз.
- Інтеграційні тести для кожного executor (ComfyUI, FFmpeg, TTS, Publisher).

## 22. Безпека

- Не комітити секрети.
- Використовувати `integration_secret` для збереження токенів.
- mTLS для worker-ів за потреби (`NODE_MTLS_REQUIRED=true`).
- Setup-токен з лімітом спроб і терміном дії.
- Усі секрети зберігаються у `/opt/vertep/config/` з permissions `0600`.
- TLS сертифікати: веб (`vertep.crt`/`vertep.key`) + node CA (`node-ca.crt`/`node-ca.key`).

  - `vertep_postgres-data`
  - `vertep_redis-data`
  - `vertep_storage`
  - `vertep_logs`
  - `vertep_models`
  - `vertep_configs`

## 25. Заборонено

## 27. Стиль роботи та відповідей агентів

### 27.1 Стислість

- Відповіді агента повинні бути максимально стислими.
- Не описувати внутрішній процес міркування.
- Не пояснювати очевидні дії, якщо користувач не попросив пояснення.
- Не повторювати поставлене завдання перед його виконанням.
- Не переказувати вміст файлів, які агент щойно прочитав.
- Не наводити довгі обґрунтування вибраного рішення без запиту користувача.
- Не виводити повний план роботи, якщо користувач його не запросив.

### 27.2 Під час виконання завдання

Проміжні повідомлення повинні бути короткими.

Допустимо:

"Перевіряю release.py і тести."

"Знайдено проблему в парсері CHANGELOG.md. Виправляю."

Не використовувати довгі повідомлення про:
- що агент збирається зробити;
- чому він це робить;
- які альтернативи він розглядав;
- покроковий reasoning;
- повторний опис архітектури проєкту.

### 27.3 Фінальна відповідь

Після виконання завдання повідомити тільки:

- що зроблено;
- які файли змінено;
- результат тестів;
- помилки або проблеми, якщо вони залишилися.

Типовий формат:

Готово.

Змінено:
- `scripts/release.py`
- `tests/test_release.py`

Перевірка:
- `pytest`: 194 passed
- `release.py --check`: OK

Не додавати детальний опис реалізації, якщо користувач його окремо не попросив.

### 27.4 Винятки

Детальне пояснення надавати лише якщо:
- користувач прямо попросив пояснити;
- потрібно повідомити про критичну помилку;
- існує ризик втрати даних;
- дія може змінити Git-історію;
- потрібне рішення або підтвердження користувача.
