# Vertep — правила для агентів

## 1. Місія проєкту

Vertep — оркестратор автоматизованої фабрики короткого медіаконтенту з віртуальними персонажами.  
Vertep **не генерує контент** — він керує інструментами, які генерують контент.  
Це мозок, диспетчер і оркестратор системи. Інструменти: Ollama, ComfyUI, FFmpeg, TTS, Publisher-модулі.

Ключовий принцип:  
> Вертеп — це конвеєр. Моделі змінюються. GPU змінюються. Workflow змінюються. Персонажі додаються й закриваються. А Vertep залишається центральною системою.

---

## 2. Мова

- Користувацькі описи, коміти, нотатки релізів, UI — **українською**.
- Технічні терміни — англійською: API, Docker, PostgreSQL, Redis, ComfyUI, FFmpeg, Ollama, job, scene, task, workflow, worker, CORE, GPU Node, Text Node, Voice Node, Publisher Node, Backup Node, Monitoring Node.
- Відповідь користувачу завжди Українською мовою. 

---
## 3. Версіонування, Push та Release

### 3.1 Загальний принцип

У Vertep використовуються дві користувацькі команди верхнього рівня:

`пуш`

та:

`реліз`

Це різні операції.

Команда `пуш`:
- готує нову версію;
- оновлює релізні файли;
- виконує перевірки;
- створює один версійний commit;
- відправляє його в `main`;
- не створює Git tag;
- не створює GitHub Release;
- не запускає release workflow.

Команда `реліз`:
- перевіряє стан репозиторію;
- за потреби спочатку виконує повну логіку команди `пуш`;
- після цього запускає GitHub Actions release workflow;
- не створює нового commit, якщо робоче дерево вже чисте;
- вважається завершеною лише після успішного створення повноцінного GitHub Release з усіма обов'язковими артефактами.

Загальна схема:

`зміни → пуш → main → реліз → GitHub Actions → runtime bundle → tag → GitHub Release`

---

### 3.2 Нумерація версій

Формат версії:

`0.0.0.X`

Нумерація послідовна.

Кожен новий commit, який потрапляє в `main`, отримує власний наступний послідовний номер.

Перед визначенням нової версії обов'язково:

- перевірити фактичну історію commit у `main`;
- перевірити локальні Git tags;
- перевірити remote Git tags;
- перевірити поточний `VERSION`;
- визначити правильний номер останнього commit;
- визначити наступний вільний послідовний номер.

Перевірка локальних tags:

`git tag --list | Select-String "0\.0\.0\."`

Перевірка remote tags:

`git ls-remote origin --tags | Select-String "0\.0\.0\."`

Якщо номер уже використаний:

- не переписувати історію;
- не переміщувати існуючий tag;
- не використовувати номер повторно;
- вибрати наступний правильний вільний номер.

Помилки в історичних назвах commit не повинні порушувати подальшу правильну нумерацію.

---

### 3.3 Commit і Push — різні операції

Commit і Push не є однією Git-операцією.

Commit:
- створює запис у локальній Git-історії;
- має власний SHA;
- у Vertep має власний номер версії.

Push:
- передає вже створений commit у remote repository;
- сам по собі не створює нового commit;
- сам по собі не створює нової версії.

Один технічний `git push` може передати декілька commit, але це не об'єднує їх в одну версію.

Кожен окремий новий commit у `main` враховується як окрема одиниця історії та нумерації.

Для штатної роботи Vertep необхідно дотримуватися принципу:

`одна версія = один commit`

---

### 3.4 Назва нового commit

Назва нового версійного commit повинна містити тільки номер версії.

Формат:

`<версія>`

Приклад:

`0.0.0.94`

Заборонено використовувати для нових commit формат:

`0.0.0.94 — опис`

або інші додаткові тексти після номера.

Детальний опис змін зберігається у:

- `CHANGELOG.md`;
- `releases/<версія>.md`;
- GitHub Release.

---

### 3.5 Один версійний commit

Усі зміни однієї версії повинні входити в один commit.

Цей commit повинен містити:

- зміни коду;
- зміни конфігурації;
- зміни тестів;
- зміни документації;
- оновлений `VERSION`;
- оновлений `CHANGELOG.md`;
- `releases/<версія>.md`.

Заборонено:

- створювати окремий commit для коду, а потім окремий commit для `VERSION`;
- створювати окремий commit для `CHANGELOG.md`;
- створювати окремий commit для release notes;
- створювати автоматичний commit після версійного commit;
- створювати технічний commit між версійним commit і його майбутнім Git tag.

---

### 3.6 Команда `пуш`

Коли користувач у чаті дає команду:

`пуш`

агент повинен виконати повний процес підготовки нової версії та її відправлення в `main`.

Команда `пуш` є користувацькою командою верхнього рівня і не означає лише виконання `git push`.

Послідовність виконання:

1. Перевірити поточний стан Git repository.

2. Визначити всі фактичні зміни відносно останнього commit.

3. Визначити наступну правильну версію `0.0.0.X`.

4. Перевірити, що ця версія не зайнята існуючим commit/tag.

5. Оновити файл:

`VERSION`

Він повинен містити тільки нову версію.

6. Оновити:

`CHANGELOG.md`

Для нового commit створити блок:

`## ПРАВИЛЬНА НАЗВА: <версія>`

Під ним описати фактичні зміни українською мовою.

7. Створити:

`releases/<версія>.md`

8. Виконати всі обов'язкові перевірки.

9. Переконатися, що всі необхідні файли входять у майбутній commit.

10. Створити один commit з назвою:

`<версія>`

11. Перевірити SHA створеного commit.

12. Виконати push цього commit у `main`.

13. Перевірити, що `origin/main` містить потрібний commit.

14. Завершити операцію.

Після успішного `пуш` агент повинен зупинитися.

Команда `пуш` НЕ повинна:

- створювати Git tag;
- створювати GitHub Release;
- запускати release workflow;
- збирати runtime bundle;
- публікувати Docker images як release;
- створювати додатковий commit після основного commit.

---

### 3.7 Формат CHANGELOG.md

Для нових версій використовується формат:

`## ПРАВИЛЬНА НАЗВА: <версія>`

Приклад:

`## ПРАВИЛЬНА НАЗВА: 0.0.0.94`
`- Виправлено логіку створення release notes.`
`- Додано перевірку runtime bundle.`

Між заголовком і першим пунктом опису порожній рядок не вставляти.

Між пунктами опису порожні рядки не вставляти.

Порожній рядок дозволений перед наступним блоком:

`## ПРАВИЛЬНА НАЗВА: ...`

Для історичних commit з неправильною оригінальною назвою використовується:

`## ПРАВИЛЬНА НАЗВА: <правильна версія>`
`## ОРИГІНАЛЬНА НАЗВА: <фактичний Git subject>`
`- <опис змін>`

`ОРИГІНАЛЬНА НАЗВА` копіюється з Git без виправлення, перекладу або нормалізації.

---

### 3.8 Формат releases/<версія>.md

Для кожної нової версії обов'язково створюється:

`releases/<версія>.md`

Приклад:

`releases/0.0.0.94.md`

Перший рядок файла повинен мати строго визначений формат:

`# Vertep <версія>`

Приклад:

`# Vertep 0.0.0.94`

Назва файла, значення `VERSION` та версія в заголовку повинні повністю збігатися.

Заборонені альтернативні заголовки:

- `# Реліз <версія>`;
- `# Release <версія>`;
- `# Vertep Release <версія>`;
- будь-які інші варіанти.

Після заголовка розміщується український опис фактичних змін версії.

Опис повинен відповідати фактичним змінам commit та `CHANGELOG.md`.

Якщо перевірка повідомляє:

`Файл нотаток релізу містить неправильну версію`

спочатку перевірити:

- значення `VERSION`;
- назву `releases/<VERSION>.md`;
- перший рядок `releases/<VERSION>.md`;
- відповідність усіх трьох значень.

Не послаблювати перевірку в коді для обходу неправильно сформованого release notes файла.

---

### 3.9 Перевірки перед commit і push

Перед створенням версійного commit обов'язково виконати:

`python -m compileall -q core adapters worker scripts installer tests`

`python -m pytest -q`

`git diff --check`

Перевірити:

- відсутність нових помилок тестів;
- відсутність синтаксичних помилок;
- відсутність секретів;
- відсутність паролів;
- відсутність API keys;
- відсутність приватних ключів;
- відсутність випадково доданих конфіденційних даних.

Також перевірити узгодженість:

`VERSION = версія commit = версія CHANGELOG = версія releases/<версія>.md`

Перед push:

- commit повинен існувати;
- назва commit повинна бути `<версія>`;
- `git status` повинен бути чистим;
- SHA commit повинен бути визначений;
- після створення commit його SHA не повинен змінюватися.

---

### 3.10 Команда `реліз`

Коли користувач у чаті дає команду:

`реліз`

агент повинен опублікувати актуальний стан `main` як повноцінний Vertep Release.

Команда `реліз` є надбудовою над командою `пуш`.

Спочатку агент обов'язково перевіряє стан repository.

Якщо є змінені, створені або видалені файли, які ще не включені в commit:

`реліз → пуш → GitHub Actions`

Тобто агент спочатку виконує повну логіку команди `пуш`.

Якщо робоче дерево чисте:

`реліз → GitHub Actions`

У цьому випадку:

- новий commit не створювати;
- `VERSION` не змінювати;
- `CHANGELOG.md` не змінювати;
- новий `releases/<версія>.md` не створювати;
- використовувати поточний версійний commit.

Перед запуском release workflow перевірити:

- `git status` чистий;
- поточний `VERSION` валідний;
- останній commit має правильну назву;
- `CHANGELOG.md` містить поточну версію;
- `releases/<VERSION>.md` існує;
- його перший рядок дорівнює `# Vertep <VERSION>`;
- commit присутній в `origin/main`;
- SHA локального commit та потрібного commit у `origin/main` узгоджені.

Після цього запустити GitHub Actions release workflow.

---

### 3.11 Єдиний власник Release

GitHub Actions release workflow є єдиним механізмом, який завершує створення повноцінного Vertep Release.

Агент під час команди `пуш` не створює Release.

Локальний release script не повинен створювати конкуруючий Release паралельно з GitHub Actions.

Не повинно існувати двох незалежних механізмів, які одночасно:

- створюють один Git tag;
- створюють один GitHub Release;
- публікують один runtime bundle.

Відповідальність за фінальну публікацію повинна бути однозначною.

---

### 3.12 GitHub Actions release workflow

Release workflow повинен працювати з конкретним уже існуючим версійним commit у `main`.

Workflow не повинен змінювати вихідний код або Git-історію.

Послідовність:

1. Checkout потрібного commit.

2. Визначення `VERSION`.

3. Перевірка узгодженості версії.

4. Запуск тестів.

5. Збірка всіх обов'язкових Docker images.

6. Збірка runtime bundle:

`vertep-runtime-<версія>.tar.gz`

7. Формування manifest.

8. Формування SHA256 checksums.

9. Формування SBOM.

10. Формування цифрового підпису.

11. Перевірка всіх обов'язкових артефактів.

12. Лише після успішного завершення всіх попередніх етапів — фінальна публікація Release.

Якщо будь-який обов'язковий етап завершується помилкою:

- workflow завершується з помилкою;
- реліз не вважається завершеним;
- агент не створює автоматично нову версію;
- агент не створює додатковий commit для обходу помилки.

---

### 3.13 Створення Git tag і GitHub Release

Git tag та GitHub Release створюються тільки після успішного проходження обов'язкових build/test етапів release workflow.

Git tag:

`<VERSION>`

повинен вказувати на SHA саме того версійного commit, з якого було виконано build.

Заборонено:

- переміщувати існуючий release tag;
- перезаписувати tag іншого commit;
- використовувати один tag для різних SHA;
- створювати tag до визначення конкретного release commit.

GitHub Release повинен відповідати тому самому `VERSION` і Git tag.

---

### 3.14 Runtime bundle

Кожен повноцінний Vertep Release обов'язково повинен містити:

`vertep-runtime-<версія>.tar.gz`

Runtime bundle повинен містити необхідні runtime-файли, зокрема:

- `docker-compose.yml`;
- `docker-compose.amd.yml`;
- `docker-compose.nvidia.yml`;
- `manifest.json`;
- `node_roles.json`;
- `deployment-plan.py`;
- `update-agent.py`;
- `vertep` CLI;
- SBOM;
- systemd unit files;
- конфігурацію monitoring.

Manifest повинен містити SHA256 необхідних файлів і цифровий підпис.

У GitHub Repository Secrets повинен бути налаштований:

`RUNTIME_SIGNING_PRIVATE_KEY`

Якщо runtime bundle відсутній, реліз не вважається повноцінним.

---

### 3.15 Source code archives не є Vertep Runtime

GitHub може автоматично показувати:

`Source code (zip)`

та:

`Source code (tar.gz)`

Ці файли не є runtime bundle Vertep.

Їх наявність не означає успішного завершення release workflow.

Повноцінний Release повинен містити щонайменше:

`vertep-runtime-<VERSION>.tar.gz`

та всі інші обов'язкові артефакти, визначені release workflow.

Якщо GitHub Release містить тільки:

- `Source code (zip)`;
- `Source code (tar.gz)`;

такий Release вважається неповним і невалідним для production-інсталяції Vertep.

---

### 3.16 Docker images

Усі Docker images одного Release збираються з одного SHA.

Версійний tag кожного image повинен точно відповідати `VERSION`.

Workflow повинен:

- зібрати всі обов'язкові images;
- опублікувати version tag;
- за потреби опублікувати `latest`;
- записати immutable digest кожного image у manifest.

Production installation повинна використовувати immutable digest.

Заборонено використовувати тільки `latest` як джерело production-версії.

Якщо хоча б один обов'язковий Docker image не зібрався, Release не вважається успішним.

---

### 3.17 Перевірка після Release

Після завершення release workflow обов'язково перевірити:

- workflow завершився успішно;
- Git tag існує;
- Git tag вказує на правильний SHA;
- GitHub Release існує;
- версія GitHub Release відповідає `VERSION`;
- `vertep-runtime-<VERSION>.tar.gz` присутній;
- manifest присутній;
- checksums присутні;
- SBOM присутній;
- необхідні підписи присутні;
- всі обов'язкові Docker images створені;
- Docker image digests відповідають manifest;
- після версійного commit не створено додатковий автоматичний commit.

Release вважається завершеним тільки після успішного проходження цієї перевірки.

---

### 3.18 Поведінка при помилці Release

Якщо GitHub Actions release workflow завершується помилкою:

- не створювати автоматично наступну версію;
- не створювати порожній технічний commit;
- не змінювати `VERSION` лише через помилку workflow;
- не виконувати amend існуючого опублікованого commit;
- не виконувати rebase;
- не виконувати force push;
- не переміщувати існуючі tags.

Спочатку визначити фактичну причину помилки.

Якщо виправлення потребує зміни файлів repository, воно є новою зміною коду і повинно пройти через нову команду `пуш` з наступною правильною версією.

Після цього команда `реліз` запускається для нової версії.

Якщо проблема не потребує зміни repository і пов'язана лише з зовнішнім середовищем або повторним запуском workflow, дозволяється повторно запустити release workflow для того самого незміненого SHA.

---

### 3.19 Нормалізація історії commit

Під час аналізу, документування або відновлення історії кожному commit визначається правильний послідовний номер:

`0.0.0.X`

Правильний номер визначається за фактичною послідовністю commit у `main`.

Кожен commit враховується, навіть якщо:

- не має номера версії;
- створений агентом;
- створений ботом;
- має технічну назву;
- має неправильний номер;
- дублює номер іншого commit;
- у старій нумерації номер було пропущено.

Кожен commit враховується один раз.

Нумерація повинна бути безперервною.

Два різні commit не можуть мати одну `ПРАВИЛЬНУ НАЗВУ`.

---

### 3.20 Правильно названий історичний commit

Якщо version prefix оригінального Git subject відповідає правильному послідовному номеру, використовувати:

`## ПРАВИЛЬНА НАЗВА: <версія>`
`- <зміна 1>`
`- <зміна 2>`

У цьому випадку:

`ОРИГІНАЛЬНА НАЗВА`

не виводити.

Для визначення відповідності порівнюється version prefix, а не весь текст старого Git subject.

---

### 3.21 Неправильно названий історичний commit

Якщо version prefix не відповідає правильному номеру або commit не має version prefix:

`## ПРАВИЛЬНА НАЗВА: <правильний номер>`
`## ОРИГІНАЛЬНА НАЗВА: <фактичний Git subject>`
`- <фактична зміна 1>`
`- <фактична зміна 2>`

`ОРИГІНАЛЬНА НАЗВА` копіюється без змін.

Вона не перекладається, не виправляється і не нормалізується.

---

### 3.22 Опис історичного commit

Опис історичного commit формується за фактичним вмістом commit.

Використовувати:

- `git show`;
- diff;
- список змінених файлів;
- фактичні зміни функцій;
- класи;
- конфігурації;
- тести;
- документацію.

Правила:

- опис українською;
- використовувати маркований список;
- не вигадувати зміни;
- не покладатися лише на Git subject;
- технічні назви оформлювати в `code`;
- суттєві зміни не приховувати;
- дрібні пов'язані зміни дозволено об'єднувати в один логічний пункт.

---

### 3.23 Заборона переписування історії

Для нормалізації або виправлення старої нумерації заборонено:

- `git rebase`;
- `git commit --amend` для старих опублікованих commit;
- `git reset` з метою перебудови опублікованої історії;
- `git push --force`;
- `git push --force-with-lease`;
- змінювати SHA існуючих опублікованих commit;
- переміщувати існуючі release tags;
- видаляти історичні commit через неправильну назву;
- squash старих commit лише заради виправлення нумерації.

Нормалізація змінює лише документальне представлення історії.

Фактичні:

- SHA;
- Git subjects;
- tags;
- GitHub Releases;
- порядок commit

залишаються незмінними.

---

### 3.24 Нова нумерація після історичних помилок

Якщо стара видима нумерація розійшлася з реальною послідовністю:

1. Визначити правильну послідовність commit.
2. Призначити кожному правильну документальну версію.
3. Зафіксувати розбіжності через `ПРАВИЛЬНА НАЗВА` та `ОРИГІНАЛЬНА НАЗВА`.
4. Не переписувати Git history.
5. Визначити правильний номер останнього commit.
6. Наступний новий commit отримує наступний номер після правильного номера останнього commit.
7. Перед використанням номера перевірити існуючі tags.
8. Якщо номер конфліктує з існуючим історичним tag, не перезаписувати його.
9. Використати наступний безпечний номер та задокументувати розбіжність.

---

### 3.25 Форматування нормалізованої історії

Всередині одного блоку commit порожні рядки заборонені.

Правильно:

`## ПРАВИЛЬНА НАЗВА: 0.0.0.94`
`- <зміна 1>`
`- <зміна 2>`

Або:

`## ПРАВИЛЬНА НАЗВА: 0.0.0.85`
`## ОРИГІНАЛЬНА НАЗВА: <оригінальний Git subject>`
`- <зміна 1>`
`- <зміна 2>`

Не вставляти порожній рядок:

- після `ПРАВИЛЬНА НАЗВА`;
- між `ПРАВИЛЬНА НАЗВА` та `ОРИГІНАЛЬНА НАЗВА`;
- після `ОРИГІНАЛЬНА НАЗВА`;
- між пунктами опису.

Один порожній рядок дозволений тільки перед наступним:

`## ПРАВИЛЬНА НАЗВА: ...`

---

### 3.26 Коротка схема команд

Команда:

`пуш`

означає:

`аналіз змін → нова версія → VERSION → CHANGELOG → releases/<версія>.md → tests → commit → push main → STOP`

Команда:

`реліз`

при наявності незакомічених змін означає:

`пуш → перевірка origin/main → GitHub Actions → build → runtime bundle → validation → tag → GitHub Release → artifacts → verification`

Команда:

`реліз`

при чистому repository означає:

`перевірка поточної версії → перевірка origin/main → GitHub Actions → build → runtime bundle → validation → tag → GitHub Release → artifacts → verification`

Головне правило:

`пуш` готує і публікує commit у `main`.

`реліз` перетворює вже опублікований commit у повноцінний Vertep Release.

## 4. Архітектурні принципи

### 4.1 CORE не генерує контент
- Всі генерації (текст, зображення, відео, голос) виконуються worker-ами через адаптери.
- CORE лише диспетчеризує задачі (`task`) і збирає артефакти.

### 4.2 Персонажі — конфіги, не код
- Нові персонажі додаються через `/characters/<id>/` директорію.
- Кожен має: `character.json`, `system_prompt.txt`, `voice.json`, `visual.json`, `generation.json`, `publishing.json`.
- Не додавати персонажів у хардкод.

### 4.3 Workflow — окремо від коду
- ComfyUI workflow зберігаються в `/workflows/`.
- CORE лише передає шлях workflow в задачі.
- Зміна моделі/LoRA/sampler не потребує зміни коду CORE.

### 4.4 Publisher — модульний
- Кожна платформа (YouTube, TikTok, Facebook, Instagram, Threads) — окремий адаптер.
- CORE передає готовий ролик і метадані, Publisher виконує публікацію.

### 4.5 Web UI
- Локалізація: українська (`admin-uk.js`, `admin-uk.css`).
- Дії: Pause / Resume / Retry / Regenerate / Cancel / Delete / Approve / Publish.

### 4.6 Інсталяція — Deployment Wizard
- Один bootstrap.sh на чисту Ubuntu 24.04.
- Користувач вибирає роль вузла: Core / GPU / Text / Voice / Publisher / Backup / Monitoring.
- Кожна роль встановлює лише необхідні компоненти.
- Після bootstrap — First Run Wizard через Web UI.
- Після завершення — користувач працює виключно через Web UI (Zero Shell).
- Всі сервіси — у Docker контейнерах, volumes для даних.
- Секрети генеруються автоматично, зберігаються у внутрішньому сховищі.

### 4.7 Immutable Runtime
- Користувач не змінює контейнер вручну.
- Будь-які зміни — через Web UI або офіційні оновлення.
- Якщо контейнер пошкоджено — замінюються новим образом.
- Усі дані, конфігурація, БД — у volumes.

```
NEW → SCRIPTING → SCRIPT_READY → ASSET_GENERATION → ASSETS_READY → 
VIDEO_GENERATION → VIDEO_READY → ASSEMBLY → READY → PUBLISHING → PUBLISHED
```

Бокові стани: `PAUSED`, `FAILED`, `CANCELLED`, `WAITING_FOR_SYSTEM`.

## 6. Джерела контенту

Перше джерело — Telegram. Подальші (RSS, сайти, API, ручне створення, тренди) додавати як модулі, не змінюючи ядро.

## 7. Ролі вузлів

- `core` — CORE + API + Dispatcher + Scheduler + Publisher + Redis + PostgreSQL + License Manager + Update Agent + Monitoring.
- `gpu` — Worker + ComfyUI + CUDA Runtime + Update Agent.
- `text` — Worker + Ollama + LLM Runtime + Update Agent.
- `voice` — Worker + TTS Runtime + Voice Models + Update Agent.
- `publisher` — Publisher Worker + платформи + Update Agent.
- `backup` — Backup Service + Snapshot Manager + Archive Service + Update Agent.
- `monitoring` — Grafana + Prometheus + Logs + Metrics + Update Agent.

Додаткові ролі активуються через `NODE_ADDITIONAL_ROLES` у `.env`.

---

## 8. Capability-driven архітектура

- Роль визначає, що встановити.
- Capabilities визначають, що вузол реально може виконувати.
- Dispatcher шукає вузол за потрібною capability, а не за роллю.
- Приклад capabilities: `image_generation`, `image_upscale`, `controlnet`, `inpainting`, `video_generation`, `tts`, `publish_youtube`, `publish_tiktok`.
- Worker сам повідомляє Core свої capabilities при реєстрації.

---

## 9. Відмовостійкість

- `recover_after_restart()` відновлює Job після перезавантаження CORE.
- Worker надсилають heartbeat.
- Після reboot основні компоненти запускаються автоматично через systemd.
- Startup recovery service відновлює стан системи.

---

## 10. Глобальні стани системи

```
NORMAL — штатна робота.
MAINTENANCE — нові задачі лише накопичуються.
UPDATING — жодні задачі не запускаються.
RECOVERING — відновлення після невдалого оновлення.
READ_ONLY — тільки читання.
EMERGENCY — лише аварійні дії адміністратора.
```

Усі модулі орієнтуються на глобальний стан через `get_system_state()`.

## 11. Safe Update System

### 11.1 Джерело оновлень
- Оновлення отримуються виключно з `https://update.vertep.ai` (або вказаного `VERTEP_UPDATE_SERVER`).
- GitHub використовується лише командою розробки.

### 11.2 Запуск оновлення
- Автоматично: періодична перевірка (раз на 6 годин через systemd timer).
- Через Web UI: Settings → Update → Install.
- Через CLI: `vertep update`.

### 11.3 Перехід у Maintenance
- Перед оновленням система переходить у `MAINTENANCE`.
- Dispatcher перестає видавати нові задачі.
- Активні задачі продовжують виконуватися.
- Нові задачі отримують `WAITING_FOR_SYSTEM`.

### 11.4 Drain Mode
- Dispatcher переходить у `DRAIN`.
- Нові задачі не запускаються.
- Worker завершують поточну роботу і повідомляють Core: `FREE`.

### 11.5 Backup перед оновленням
- Автоматично створюється резервна копія: конфігурація, PostgreSQL, Redis, локальні налаштування, ліцензії, секрети, журнали міграцій.
- Зберігається у `/opt/vertep/backups/update-<stamp>/`.

### 11.6 Оновлення
- Завантажуються нові контейнери.
- Виконується міграція БД.
- Перезапускаються сервіси.

### 11.7 Health Check після оновлення
- Перевірка: PostgreSQL, Redis, API, Web UI, Ollama, Dispatcher, GPU, Driver, CUDA, ComfyUI, VRAM.
- Кожен Worker проходить самотестування (мінімальний workflow).
- Лише після успішного завершення: `STATUS = READY`.

### 11.8 Rollback
- Якщо будь-який Health Check завершився помилкою — оновлення скасовується.
- Автоматично виконується: відновлення попередньої версії, контейнерів, БД, запуск попередньої конфігурації.
- `vertep rollback` — ручний rollback через CLI.

### 11.9 Rolling Update
- Оновлює вузли по одному (one-node-at-a-time).
- Canary promotion: перший вузол оновлюється, проходить self-test, потім підтверджується (promote) або відкочується (rollback).
- Підтримка порядків: `workers-first`, `core-first`, `custom`.
- Автоматичний rollback при таймауті або помилці.

### 11.10 Логування
- Окремий журнал оновлень: `/data/config/update/status.json`, `/data/config/update/log/`.
- Кожен запис: час, фаза, статус, повідомлення.

## 13. First Run Wizard

### 13.1 Кроки
1. **Роль вузла** — вибір зі списку. Для non-Core: введення Core URL, Core Certificate, Registration Token.
2. **Назва інсталяції** — ім'я системи, домен (необов'язково).
3. **Адміністратор** — login, password, підтвердження.
4. **Секрети** — автоматично згенеровані, користувач бачить лише повідомлення.
5. **Обладнання** — автовизначення GPU, RAM, CPU.
6. **AI Backend** — Ollama / External OpenAI / External API / Skip.
7. **Health Check** — автоматична перевірка всіх сервісів.
8. **Installation Manifest** — перегляд, можливість завантажити JSON.
9. **Готово** — Installation ID, Core URL, Core Certificate, Registration Token.

### 13.2 Core Wizard
- Генерує перший Registration Token для підключення Worker-ів.
- Відображає Core Certificate для імпорту на Worker-и.

### 13.3 Non-Core Wizard
- Вводить Core URL, Core Certificate, Registration Token.
- Отримує JWT, Worker Secret, Configuration.
- Реєструється у Core через `/api/nodes/register`.

## 14. Registration Token

- Генерується Core для підключення Worker-ів.
- Формат: `VT-XXXX-XXXX-XXXX` (32 hex символи).
- TTL: 15 хвилин (за замовчуванням).
- Зберігається в базі даних (`node_registration_tokens`).
- Використовується один раз, потім видаляється.

---

## 15. Node Registry

- Core веде реєстр усіх вузлів.
- Кожен вузол має: `node_id`, `role`, `capabilities`, `hardware`, `version`, `status`, `last_heartbeat`.
- Worker надсилає heartbeat кожні 30 секунд.
- Core автоматично визначає `ONLINE / BUSY / FREE / UPDATING / OFFLINE / ERROR`.

---

## 16. Worker Registration Flow

1. Bootstrap встановлює роль, генерує CSR.
2. Користувач вводить Core URL + Registration Token у Wizard.
3. Worker відправляє `/api/nodes/register` з CSR, capabilities, hardware.
4. Core перевіряє токен, видає JWT + Worker Secret + Configuration.
5. Worker зберігає credentials, запускає сервіси.
6. Worker з'являється у Web UI Core.

---

## 17. GPU Dispatcher

- CORE постійно знає стан усіх WORKER.
- При створенні GPU-задачі вказуються вимоги: `IMAGE / MIN_VRAM 6 GB` або `VIDEO / MIN_VRAM 20 GB`.
- Dispatcher сам визначає, на яку машину відправити задачу.
- Підтримує різні GPU: NVIDIA, AMD.
- Worker сам повідомляє свої capabilities при реєстрації.

## 18. Сценарний агент

- Генерація сценарію — багатоступінчаста:
  1. **Structure**: заголовок, опис, хештеги, план сцен.
  2. **Scenes**: для кожної сцени окремий LLM-виклик з промптом персонажа + сценарію.
  3. **Assembly**: збір фінального script, нормалізація через `ScriptDocument`.
- Реалізація: `core/script_agent.py`.
- Виклик: `ScriptAgent().generate_script()` в `core/pipeline.py:prepare_job()`.
- Fallback: якщо сцена невалідна — перегенерувати лише її, не весь сценарій.
- Персонаж передається як конфіг, не хардкод.

---

## 19. ComfyUI Executor

- Додавати в `worker/role_executor.py` як `execute_image()`/`execute_video()`.
- Реєструвати в `EXECUTORS`/`ROLE_TASKS`.
- Не викликати `ComfyUIAdapter` напряму в `worker/service.py` — використовувати `execute_role_task()`.
- Fallback для відео: якщо ComfyUI не повернув відео — зібрати з кадрів через FFmpeg.

---

## 20. FFmpeg пайплайн

- Збірка виконується через `FFmpegAdapter` в `core/pipeline.py:finalize_job()`.
- Не переносити на worker без явного завдання.
- Підтримує: відеоряд, pan/zoom, переходи, голос, музика, субтитри, заставки, фінальне кодування.
- Принцип: не витрачати GPU на те, що нормально робиться звичайним монтажем.

---

## 21. Тестування

- Перед кожним релізом: `python -m pytest -q`.
- Допустимі невдачі: тільки e2e через `ERR_CONNECTION_REFUSED 127.0.0.1:8080` (браузерні тести без запущеного сервера).
- Будь-які нові падіння в `tests/test_features.py` або інших модульних тестах — блокують реліз.
- Інтеграційні тести для кожного executor (ComfyUI, FFmpeg, TTS, Publisher).

---

## 22. Безпека

- Не комітити секрети.
- Використовувати `integration_secret` для збереження токенів.
- mTLS для worker-ів за потреби (`NODE_MTLS_REQUIRED=true`).
- Setup-токен з лімітом спроб і терміном дії.
- Усі секрети зберігаються у `/opt/vertep/config/` з permissions `0600`.
- TLS сертифікати: веб (`vertep.crt`/`vertep.key`) + node CA (`node-ca.crt`/`node-ca.key`).

- Усі сервіси працюють виключно в контейнерах.

  - `vertep_postgres-data`
  - `vertep_redis-data`
  - `vertep_storage`
  - `vertep_logs`
  - `vertep_models`
  - `vertep_configs`

## 25. Заборонено

- Змінювати `VERSION` або `CHANGELOG.md` в окремому коміті перед релізом.
- Створювати додатковий коміт після релізного.
- Використовувати `latest` тег для production-інсталяцій.
- Пуш в `main` без попереднього запуску тестів.
- Комітити секрети, паролі, ключі.
- Хардкодити персонажів, workflow, secrets.
- Викликати `ComfyUIAdapter` напряму в `worker/service.py` — використовувати `execute_role_task()`.
- Блокувати event loop CORE блокуючими викликами FFmpeg — використовувати `ThreadPoolExecutor`.

## 26. Принцип "Infrastructure as Product"

- Vertep сприймається як єдиний програмний продукт, не як набір окремих компонентів.
- Користувач взаємодіє лише з брендом Vertep.
- Внутрішні технології (Docker, PostgreSQL, Redis, Ollama, CUDA) — деталі реалізації.
- Весь адміністрування через Web UI, не через shell.

## 27. Стиль роботи та відповідей агентів

### 27.1 Стислість

- Відповіді агента повинні бути максимально стислими.
- Не описувати внутрішній процес міркування.
- Не пояснювати очевидні дії, якщо користувач не попросив пояснення.
- Не повторювати поставлене завдання перед його виконанням.
- Не переказувати вміст файлів, які агент щойно прочитав.
- Не наводити довгі обґрунтування вибраного рішення без запиту користувача.
- Не виводити повний план роботи, якщо користувач його не запросив.

### 27.2 Під час виконання завдання

Проміжні повідомлення повинні бути короткими.

Допустимо:

"Перевіряю release.py і тести."

"Знайдено проблему в парсері CHANGELOG.md. Виправляю."

Не використовувати довгі повідомлення про:
- що агент збирається зробити;
- чому він це робить;
- які альтернативи він розглядав;
- покроковий reasoning;
- повторний опис архітектури проєкту.

### 27.3 Фінальна відповідь

Після виконання завдання повідомити тільки:

- що зроблено;
- які файли змінено;
- результат тестів;
- помилки або проблеми, якщо вони залишилися.

Типовий формат:

Готово.

Змінено:
- `scripts/release.py`
- `tests/test_release.py`

Перевірка:
- `pytest`: 194 passed
- `release.py --check`: OK

Не додавати детальний опис реалізації, якщо користувач його окремо не попросив.

### 27.4 Винятки

Детальне пояснення надавати лише якщо:
- користувач прямо попросив пояснити;
- потрібно повідомити про критичну помилку;
- існує ризик втрати даних;
- дія може змінити Git-історію;
- потрібне рішення або підтвердження користувача.
