# Концептуально-архітектурний аудит Vertep — 13.11.2026

## Висновок і межі перевірки

Vertep має реалізовані основу CORE/Worker, контентні executors, компоненти LAB і механізм релізів. Однак повну відповідність архітектурному задуму та production-готовність не підтверджено. Виявлено конкретні розбіжності в сценарній генерації та межах автономності LAB.

- Версія: **0.0.3.72**.
- SHA: `77c8b5d51ecb6a81e0fa6c8df18e835ffc0a65bc`.
- Через `git ls-remote` підтверджено відповідність поточному `main` у GitHub на момент перевірки.
- Робоче дерево на момент аудиту було чисте.
- Метод: статичний архітектурний аудит із вибірковою перевіркою реалізації, документації та тестів. Це не повна перевірка всіх шляхів виконання.

Актуальні описи, коментарі й статуси Issues, закритих VAR, CI та Releases не перевірені: у середовищі не було `gh`, а тимчасово завантажений CLI повідомив про відсутність автентифікації. Історичні звіти репозиторію використано лише як довідку. Запуск тестів заблокований відсутністю `pytest`.

Під час аудиту код, Issues, VAR і GitHub-статуси не змінювалися. Цей файл створено згодом за прямим дорученням користувача для збереження звіту.

## Пріоритетні знахідки

### F1. P1 — production-генерація сценарію не відповідає багатоступінчастому контракту

**Вимога:** §14 AGENTS.md вимагає Structure → Scenes → Assembly і точкової перегенерації невалідної сцени.

**Доказ:** `worker/role_executor.py:112`, функція `execute_script()`, робить один запит до Ollama, розбирає JSON і нормалізує результат. `ScriptAgent` викликається лише в `DEMO_MODE`.

**Висновок:** підтверджена розбіжність коду з вимогою. Наявність багатоступінчастого класу не доводить виконання цього алгоритму production-шляхом. Перевірка й усунення розбіжності можливі без Dell R720.

Джерела: [executor](../worker/role_executor.py), [опис production-шляху](../docs/content-pipeline.md).

### F2. P1 — взаємозамінність LLM обмежена фактичним executor

**Вимога:** документація описує вибір LLM через Provider Layer, включно з OpenAI-сумісним backend.

**Доказ:** `execute_script()` безпосередньо використовує `OLLAMA_URL`, `/api/generate` та Ollama-specific payload.

**Висновок:** для цього шляху загальна обіцянка заміни backend через провайдерну конфігурацію не підтверджена. Це окрема архітектурна проблема від кількості етапів генерації.

Джерела: [контракти провайдерів](../adapters/providers/base.py), [опис провайдерів](../docs/providers.md), [executor](../worker/role_executor.py).

### F3. P1 перед активацією автономності — вбудований LAB executor виконує лише звітні завдання

**Доказ:** `lab/role_service.py` дозволяє `audit`, `review`, `report`; інші типи повертають `blocked`. Він не змінює код і не запускає тести.

**Висновок:** це не прихований дефект — обмеження прямо описане в документації. Але компоненти orchestration/governance не можна зараховувати як готову автономну лабораторію розробки.

[Контракт наскрізного циклу](../docs/lab/lab-issue-cycle.md) фіксує відкладену реалізацію до встановлення LAB на VM. Актуальність цього рішення в GitHub не звірена. Ця знахідка не є дорученням реалізувати відкладений функціонал.

Джерела: [вбудований executor](../lab/role_service.py), [опис LAB](../docs/lab.md).

### F4. P2 — звіти вбудованого LAB можуть мати недостатню кодову основу

**Доказ:** `_workspace_context()` передає список до 500 файлів; вміст читається лише для явно заданих `paths` із загальним обмеженням контексту. Без `paths` модель отримує переважно перелік файлів.

**Ризик:** успішна відповідь executor не доводить, що модель дослідила реалізацію. Такий результат має залишатися звітом, а не доказом проходження критеріїв.

Джерело: [lab/role_service.py](../lab/role_service.py), `_workspace_context()`, рядок 25 на перевіреному SHA.

### F5. P2 — синхронний inference блокує event loop LAB API

**Доказ:** асинхронний `/invoke` безпосередньо викликає `_call_model()`, який використовує блокуючий `urllib.request.urlopen()` із типовим таймаутом 600 секунд.

**Ризик:** затримки обслуговування інших запитів того самого процесу під час inference. Фактичне навантажувальне проявлення не вимірювалося; виклик підтверджений кодом.

Джерело: [lab/role_service.py](../lab/role_service.py), обробник `/invoke`, рядок 68 на перевіреному SHA.

## Релізи та історія приймання

У [release workflow](../.github/workflows/release.yml) є правильна архітектурна залежність: build очікує gate CI та Browser E2E для конкретного SHA. Публікація використовує draft із перевіркою завантажених assets. [Збирач runtime](../scripts/build-runtime-bundle.py) створює SBOM усередині bundle — відсутність окремого SBOM asset сама по собі не доводила б його відсутності.

Наявність workflow не підтверджує успішний Release. Без GitHub API не встановлено останню опубліковану версію, відповідність tag → SHA, повноту assets і результат перевірки підписів.

[Попередній аудит закритих Issues](audit-0311-closed-issues.md) описує масове закриття через перенесення залишків і довгі ланцюги наступників. Це історичне свідчення ризику обліку, **не повторно підтверджений стан GitHub**. На його підставі не можна оголошувати конкретний закритий VAR виконаним або невиконаним сьогодні.

Перевірка актуальних закритих VAR та Issues залишається заблокованою відсутністю автентифікації GitHub CLI. Не встановлено повної матриці «критерій конкретного Issue → реалізація → виконана перевірка → доказ приймання».

## Що потребує Dell R720 / VMware / GPU

| Перевірка | Чому коду й mock недостатньо |
|---|---|
| GPU passthrough, драйвери, VRAM, ComfyUI | Потрібні фактичні GPU, конфігурація VMware і запуск моделей |
| Production-priority GPU lease LAB | Потрібно виміряти revoke під реальною конкуренцією, зупинку inference і звільнення VRAM |
| Ізоляція LAB VM | Потрібні негативні проби доступу до production storage, Docker socket, мережі й GPU |
| Install / update / rollback / restore | Потрібні реальний runtime, persistent storage і контрольовані сценарії відмов |
| Наскрізний медіаконвеєр | Потрібні реальні моделі, артефакти між вузлами, TTS, FFmpeg і фінальне відео |
| Publisher | Потрібні дозволені облікові записи платформ і фактичні receipts; Dell для цього не обов’язковий |
| LAB 24/7 | Потрібні тривалий запуск, recovery, бюджети, lease і незалежна перевірка доказів |

Процедура [кваліфікації LAB R1–R6](../docs/lab/lab-qualification.md) правильно розрізняє процедуру та фактичний PASS. У цьому аудиті стендових PASS немає. Доступ до стенду, destructive tests і production-операції не виконувалися.

## Результати перевірок

- Синтаксично розібрано через Python AST **494 файли** в `core`, `lab`, `adapters`, `worker`, `scripts`, `installer`, `tests`: помилок немає.
- `git diff --check`: без помилок на момент аудиту.
- `python3 -m pytest --version`: `No module named pytest`; suite не виконано.
- AST-перевірка не замінює unit/integration/E2E tests і не підтверджує імпорти, runtime-залежності або бізнес-логіку.
- Переглянуто [CORE generation gate](../tests/test_core_generation_gate.py) та [тести кваліфікації LAB](../tests/test_lab_qualification.py); успішність їх запуску не заявляється.

## Пріоритети

1. Узгодити production script executor із погодженим багатоступінчастим контрактом і Provider Layer.
2. Підтвердити релізні докази точного SHA та актуальні критерії й результати приймання GitHub Issues/VAR після відновлення доступу.
3. Провести дозволену стендову кваліфікацію перед активацією автономного LAB; не зараховувати звіт моделі або статус задачі як PASS критеріїв.
4. Окремо оцінити обмеження контексту й блокуючий inference в LAB API.

Пріоритети є висновками аудиту, а не дозволом на зміну коду, створення Issues, запуск стендових сценаріїв, push або release.
