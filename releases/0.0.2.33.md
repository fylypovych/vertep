# Vertep 0.0.2.33

- Виправлено звіт про невідомий стан під час читання стану задачі у `adapters/providers/video_engines.py`: відповідь `404` більше не звітується як transient-помилка, а має власну причину `upstream_task_absent`, бо такий runtime нічого не тримає від спроби; транспортний збій (`timeout`/`connect error`) тепер має причину `upstream_unreachable`, а не `upstream_transient_failure` (§5, P6; `test_a_task_the_upstream_no_longer_knows_reports_absent`, `test_an_unreachable_upstream_is_unreachable_and_never_absent`).
- Додано `scripts/issue-122-acceptance-report.py` — єдиний трасований звіт P10 за матрицею §6: кожен критерій має власного owner-Issue й перелік тестів, `PASS` можливий лише коли середовище надає потрібне (container runtime / живий CORE з harness / авторизований стенд) **і** кожен задекларований тест зібрано, виконано й пройдено; `skipped`, `missing` і `FAIL` не зараховуються як виконання (§6 Evidence). Звіт пише SHA, dirty-відмітку, config revision, pinned upstream і bridge schema та завершується ненульовим кодом при `FAIL`.
- Browser-критерій звіту більше не стає `PASS`, коли `VERTEP_E2E_STATE_DIR` не адресує сховище стану запущеного CORE: без нього system-state перевірка мовчки пропускається, а пропуск не є доказом.
- Виправлено Browser E2E очікування для P8: після переведення `MoneyPrinterTurbo` на інший runtime повторне введення попередньої адреси — це знову зміна ефективної конфігурації, тому кнопка «Застосувати» лишається доступною, а не блокується як після першого застосування (`test_settings_video_engine_repoints_the_runtime_of_the_current_engine`).
- Додано `scripts/issue-122-retirement-trace.py` — простежка P12: читає канонічну таблицю перекриття #122, розбирає кожен рядок на ланцюг «критерій → заміна/власник → parity evidence → рішення» і показує, що жоден рядок не списуємо автоматично; остаточне рішення власника про old-list не підміняється скриптом (§8).
- Додано `tests/test_full_media_e2e.py` (#82): наскрізний First Run → Text Worker → storyboard → image/voice Worker → assembly → video approval через справжні чергу, claim і результат штатними шляхами CORE, з двома revision loops, перевіркою незмінності `video_versions`, cancel, restart recovery та idempotent regenerate.
- Додано `tests/test_full_media_harness.py` (#82): структурні контрольні точки медіаконвеєра — збереження Job після перезапуску CORE, чисті переходи під час failure/cancel/lease expiry, відхилення пізнього результату скасованого Job, дедуплікація версій рендеру, а також спільні smoke-перевірки backup/update і CI-звіту (SHA, конфігурація, цілісність артефактів).
