# Vertep 0.0.4.13

- Публікація (#502, рішення власника): модуль Publishing лише показує публікації й передає дії редактора до CORE разом із підписаним Gateway короткоживучим контекстом користувача; CORE сам перевіряє права на бренд і канал та пише в аудит реального користувача. Власна БД і логіка відправлення прототипу прибрані — відправляє Worker.
- Канали (#502): один набір облікових даних на канал, Worker отримує лише секрет каналу свого завдання. Новий канал без секрету блокує публікацію з чіткою помилкою; глобальні облікові дані платформи — лише за явним дозволом адміністратора (з аудитом і попередженням). Панель «Облікові дані» в каналах бренду.
- Автоматична публікація після погодження — за політикою каналу (бренд або перевизначення каналу) з дотриманням погоджень спільного контенту.
- Storyboard (#501): модуль без власної БД — читає сторіборди з job через API CORE; версії, ревізії й погодження лишаються в job.
- LAB (#493): спільна identity адміністратора — CORE видає короткоживуче підписане Ed25519 твердження, LAB його перевіряє.
- Monitoring (#503): модуль розміщується на будь-якому сумісному вузлі; збирає метрики, стан перевірок і тривоги з CORE (`monitoring.read`) з історією спрацювання→підтвердження→відновлення; виправлено маршрути окремої тривоги, читання JSONB і статистику. CORE працює без модуля.
- Модулі: відновлення архіву замінює рядки, засіяні міграцією, замість дублювання (раніше блокувало видалення модулів із типовими налаштуваннями).
- Web UI (#504): панель кожні 30 с повторно перевіряє CORE — відновлює з'єднання без перезавантаження й попереджає про несумісний API після оновлення CORE; показує SHA своєї збірки.
