# LAB: наскрізний цикл Issues (var.0.0.3.98, #398)

**Статус: затверджено власником 2026-11-07 після архітектурного огляду.** Цей документ сам не дозволяє реалізацію, активацію прав, запуск на стенді чи закриття Issues: для кожної такої дії потрібне окреме доручення. За рішенням власника від 2026-11-06 реалізація відкладена до встановлення LAB на реальну VM (#329).

Код звірено на `d6fca20fd2eb1b39381bfee6bde2a4102dc2e7a5` (0.0.3.50). Тести й стенд для цієї звірки не запускались.

## Схема

```
пакет власника → синхронізація → план → виконання → докази → незалежна перевірка → закриття
```

Ланцюг запускається лише для пакета, який явно видав власник. Будь-яка відсутня ланка зупиняє цикл, Issue лишається відкритим.

## Контракт 0: пакет власника

- Зміст: `package_id`, перелік Issues (`number` і `identifier`), цільовий повний SHA, версія, стенд, спосіб перевірки кожного критерію, залежності, дозволені дії, строк grant.
- Зберігання: у стані LAB, поза робочою копією виконавця. Виконавець і перевіряльник пакет лише читають.
- Зв'язки «критерій → перевірка» готує LAB як чернетку, затверджує власник у складі пакета.
- Захист від підміни: власник видає пакет через наявну owner-автентифікацію, а grant прив'язується до хеша пакета через `scope`. Звірка `scope` у gate вже є (`lab/policy.py:233`), але `delegate_close_ir` і `consolidate_ir` його не передають (`lab/governance.py:573`, `:825`), а задачі `test` і `verify` виконуються без grant (`lab/orchestrator.py:313`). Тому потрібні передача хеша пакета в обидва виклики й окрема дія policy gate для старту пакета. Без збігу цикл не стартує.
- Запуски на стенді виконуються під окремим обліковим записом, указаним у пакеті.
- Зміна SHA, стенда чи переліку — це новий пакет. Докази іншого пакета не зараховуються без окремої перевірки застосовності (AGENTS §4.7).

## Контракт 1: синхронізація

- Лише читання GitHub. Імпорт нічого не змінює в Issue.
- Вхід: пакет власника. Історичні `ir` автоматично не підхоплюються (AGENTS §4.7).
- Запис Issue: `number`, `identifier`, `state`, `body_sha256`, час читання.
- Критерій: рядок `- [ ]` з Issue; `criterion_id` = `sha256` нормалізованого тексту. Зміна тексту дає новий критерій, старий доказ до нього не застосовується.
- Позначені `- [x]` критерії не зараховуються автоматично: відмітка не є доказом.
- Залежності вказує пакет власника: текст Issue не має машинного формату. Якщо критеріїв немає або їх не вдалося розібрати, стан `NEEDS_OWNER`, а не PASS.
- Без дублювання: `task_id` = `<package_id>:<identifier>:<criterion_id>:<sha>`. Наявний `enqueue` уже повертає існуючу задачу при тому самому scope і відмовляє при іншому; `package_id` дає новому пакету власні задачі.
- Читаються також коментарі. Запис Issue містить `comments_sha256`: хеш усіх коментарів, крім звітів CORE про запуски цього пакета (CORE пише їх сам, `core/api/real_tests.py:87`). Інший новий коментар зупиняє Issue зі станом `STALE`, бо він може змінювати вимоги, а автоматично це не визначити.
- Перед закриттям Issue читається ще раз. Якщо `body_sha256` або `comments_sha256` змінились, чи Issue вже закрито, цикл зупиняється зі станом `STALE`.
- Вихід зі `STALE`: звіт власнику, а той видає новий пакет. Результати незмінених критеріїв придатні без нового запуску, якщо збігаються `criterion_id`, SHA і стенд, але доказ підписується заново, бо підпис охоплює `issue_body_sha256`. Змінені критерії перевіряються знову.

## Контракт 2: план і виконання

Для кожного критерію пакет визначає спосіб перевірки: `test_ids`, `scenario` (`rt_id` з CORE) або `stand_procedure`. Сам LAB спосіб не вигадує і критеріїв не додає (AGENTS §0.3).

Стан задачі й результат критерію — різні речі:

| Поняття | Значення | Що означає |
|---|---|---|
| `RunState` задачі | PENDING, RUNNING, COMPLETED, FAILED, BLOCKED, PAUSED | Чи відпрацював механізм |
| Вердикт критерію | PASS, FAIL, BLOCKED, NOT_VERIFIED | Чи доведена вимога |

- PASS дає лише фактичний запуск на дозволеному середовищі. COMPLETED вердиктом не є.
- Collect-only, mock, skip, процедура без виконання (`PROCEDURE` у CORE) і відповідь моделі дають NOT_VERIFIED.
- Однакові критерії різних Issues можна покрити одним запуском за збігу версії, середовища й сценарію. Доказ старого SHA не застосовується автоматично.
- LAB не встановлює runtime-залежності від production CORE (AGENTS §4.7). Для сценаріїв CORE він викликає `POST /api/real-tests/run` лише на CORE дозволеного стенда й забирає звіт запуску. Логіка перевірок не копіюється в LAB.
- Деструктивні перевірки (`destructive_checks` у `prerequisites`) потребують окремого дозволу власника в пакеті. `confirm_destructive=true` дозволом не вважається: API вимагає його для будь-якого запуску (`core/api/real_tests.py:138`).
- `check_names` не передається: запускається лише повний набір сценарію, бо цей параметр може додати перевірки поза ним (`core/real_tests/runner.py:130`).
- Перед виконанням перевірка стенда: фактичні SHA й версія мають збігатися з пакетом, інакше `STALE`.
- Повтор після збою: перед запуском у стан LAB записується намір (`task_id`), після запуску — `test_run_id`. Під час відновлення LAB спершу шукає запуск за цими записами і другий не стартує. Якщо записано лише намір, результат NOT_VERIFIED, а повтор деструктивної перевірки потребує рішення власника. Задача в стані PAUSED чи BLOCKED відновлюється лише з чинним grant (`lab/orchestrator.py:190`).
- Завислий запуск: після таймауту з пакета результат NOT_VERIFIED, Issue не закривається.

## Контракт 3: докази й незалежна перевірка

До наявного формату `lab/evidence.py` додаються:

```json
{
  "identifier": "ir.0.0.3.29",
  "issue_number": 329,
  "issue_body_sha256": "<sha256>",
  "commit": "<повний SHA>",
  "version": "<VERSION>",
  "environment": {},
  "criteria": [
    {"criterion_id": "<sha256>", "verdict": "PASS", "method": "scenario",
     "run_ids": ["<id>"], "expected": "...", "actual": "...",
     "artifacts": [{"path": "...", "sha256": "..."}]}
  ]
}
```

- Для закриття потрібен PASS для кожного критерію з актуального тексту Issue. Зайві, відсутні чи чужі `criterion_id` дають відмову.
- Підпис reviewer уже охоплює весь доказ через `evidence_digest`, тож критерії теж стають підписаними.
- Походження: артефакт створює виконавець, а не автор коду; секрети в артефакти не потрапляють.
- Перевіряльник працює окремим процесом, без робочої копії й прав виконавця. Він сам читає з CORE стенда запуск за `run_ids`, SHA, версію та перевірки, а не лише переданий виконавцем файл, і тільки потім підписує. Міркувань автора не отримує, а текст артефактів вважає даними, не інструкціями.
- Для `i` стенда немає, тому перевіряльник бере результат за ідентифікатором запуску GitHub Actions або сам запускає `test_ids` у чистій копії цього SHA.
- Рішення про PASS спирається на механічні звірки; модель може лише відмовити в підписі.
- Для production і деструктивних сценаріїв підпис ставить людина власним ключем із теки довіри; ключ людини позначається в пакеті як обов'язковий, і підпис ролі LAB там не приймається.
- Приватний ключ недоступний виконавцю. Тека довіри (`LAB_REVIEW_TRUST_ROOT`) для виконавця лише для читання, інакше він міг би додати власний ключ і підписати доказ сам.
- Немає доказу, підпису, права чи зв'язку з Issue: відмова, Issue відкритий.

## Контракт 4: завершення

Єдиний шлях закриття `ir`: `delegate_close_ir`. Перед викликом перевіряються актуальний стан Issue, збіг ідентифікатора в назві, збіг SHA і стенда доказу з пакетом, усі PASS, підпис і grant `DELEGATE_CLOSE_IR`.

Після вимкнення закриття в CORE його захисти з `can_close_issue` (`core/real_tests/github.py:376-419`) переносяться сюди: сценарій відповідає Issue; запуск застосовний до цього SHA і версії на стенді; покрито всі обов'язкові перевірки сценарію, усі PASS; один запуск закриває той самий Issue лише раз, зокрема після перезапуску.

Шлях `i` окремий, бо він не потребує реального сервера: окрема дія policy gate й окремий тип доказу (`evidence_kind`, наприклад `code_in_main`). Вимоги: SHA є предком `origin/main`, `test_ids` із пакета пройшли на цьому SHA, усі критерії PASS, підпис перевіряльника. Загальний зелений CI не вимагається: commit команди `пуш` CI не має (AGENTS §2.6). Лабораторія лише перевіряє наявність коду в `main`, але не публікує його.

| Результат | Дія |
|---|---|
| `ir`, усі критерії PASS і підтверджено | Закрито як `completed` із коротким коментарем, без окремого ручного погодження (AGENTS §4.7) |
| Є FAIL, BLOCKED чи NOT_VERIFIED | Issue відкритий, звіт власнику |
| Постійний залишок | Наявний `consolidate_ir`: спочатку нові `ir`, перевірка повноти, лише тоді закриття старого як `not_planned`. Код ще не передає цю причину (див. «Знайдені дефекти») |
| `i`, код у `main`, усі критерії PASS і підтверджено | Закриває лабораторія; публікацію коду вирішує людина (див. рішення 3) |

Push, release, гілки й PR лишаються під контролем власника. Цикл їх не виконує.

## Рішення власника

1. **Хто закриває Issue перевірок CORE. Рішення власника: лабораторія.** Зараз `RealTestRunner.run` і `core/api/real_tests.py:88` закривають Issue самі, без незалежного підпису. Автоматичне закриття в CORE вимикається, CORE лише звітує.
2. **Хто є незалежним перевіряльником. Рішення власника: окрема роль LAB з окремим ключем.** Для production і деструктивних сценаріїв підпис ставить людина. Рішення власника: автор і перевіряльник можуть працювати на одній моделі за умов контракту 3. Залишковий ризик: однакове хибне розуміння вимоги, якого не виявлять механічні звірки.
3. **Закриття `i` і публікація. Рішення власника:** фінальне рішення про публікацію коду приймає людина; лабораторія закриває `i` лише після входження коду в `main` і доведення всіх критеріїв із підписом перевіряльника (§4.6, §4.7).
4. **Строк grant на закриття. Рішення власника: поки Issue не виконано.** Grant видається на конкретний Issue і втрачає силу після його закриття. Код не приймає grant без дати (`lab/policy.py:154`), а §4.6 вимагає строк, тому власник вказує далеку дату як верхню межу.
5. **#63 AC4.** Критерій вимагає автоматичного закриття, а рішення 1 прибирає його з CORE. Рішення власника: перед реалізацією змінити критерій так, щоб закриття перевірялось через LAB. Текст #63 ще не змінено.

## Знайдені дефекти (поза цим var, не виправлялись)

- `delegate_close_ir` для Issue, створеного не лабораторією, бере номер із `evidence.issue_number` і не звіряє його з ідентифікатором у назві Issue (`lab/governance.py:580`). Grant на один `ir` разом із підписаним доказом, де вказано інший номер, закриє чужий Issue.
- `lab/evidence.py:23` звіряє ідентифікатор лише для значень із префіксом `ir.`: для числового номера й історичних `ri.`, `rt.` ця перевірка не діє.
- `consolidate_ir` закриває джерело без `not_planned`: `close_issue` надсилає лише `state: closed` (`lab/governance.py:288`, `:888`). Це суперечить AGENTS §4.7. Яку причину GitHub ставить за замовчуванням, не перевірялось.

Перші два випадки потребують grant власника, третій — дії з `consolidate_ir`; до впровадження циклу жоден не є автоматичним. У разі реалізації етапу 6 ці виправлення обов'язкові.
