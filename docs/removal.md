# Видалення інсталяції Vertep

> Статус: локальна реалізація; Ubuntu/systemd qualification окрема | Аудиторія: оператор, розробник | Канон: [AGENTS.md](../AGENTS.md) §0.4; погоджений контракт #446; повне видалення з копією — #524.

## Обсяг

`sudo vertep remove` повністю видаляє поточну інсталяцію: БД і її volumes, локальні дані, конфігурацію, компоненти й модулі, їхні контейнери, служби та файли. Видаляються лише підтверджені ресурси інсталяції. Підтримується нестандартний installation root: wrapper визначає його від власного розташування; Python executor також приймає явний `--root`. Команда доступна в новому runtime bundle; старий встановлений CLI сам собою не оновлюється від локальної зміни репозиторію.

Перед переглядом чи видаленням потрібен `config/removal-ownership.json`, записаний інсталятором із переліку файлів runtime. Bootstrap реєструє inventory після отримання підписаного runtime та оновлює його після встановлення служб; синхронізація host runtime під час update також оновлює inventory. Файли, units, Docker image IDs, networks і volumes зберігаються з installation identity. Зміна зафіксованого файла або unit блокує автоматичне видалення.

Стара інсталяція без inventory, legacy/source installer без manifest файлів, невідомі зовнішні каталоги ComfyUI/Ollama або змінені systemd drop-ins не вважаються автоматично належними Vertep. Потрібна окрема інвентаризація й рішення оператора; команда не відновлює походження пакетів чи файлів за їхніми назвами.

## Перегляд і підтвердження

Наведені команди — інструкція оператору; документація не є дозволом запускати видалення на сервері.

```bash
sudo vertep remove --dry-run
```

JSON містить root, installation ID, точні container/network/image IDs, units, файли й дані з SHA256, збережені й заблоковані ресурси та `plan_sha256`. Перегляд виконує лише читання. Значення secrets не друкуються; environment-файли не виконуються як shell-код. Повний перелік є також у журналі видалення.

Звичайний `sudo vertep remove` показує короткий підсумок: CORE і встановлені модулі з версіями, кількість ресурсів, що буде видалено, кількість збережених сторонніх/спільних ресурсів і причини блокування. Списку файлів і хешів у ньому немає. Далі команда пропонує резервну копію (`full`, `db`, `none`) і питає `YES/NO`; `NO` або інша відповідь завершує роботу без копії й без змін. Для non-interactive запуску передаються `--backup full|db|none` і `--confirm <plan_sha256>` з `--dry-run`; без `--backup` видалення не починається. Зміна переліку до виконання робить попереднє підтвердження недійсним. Після підтвердження команда сама блокує приймання нових задач і зупиняє локальні служби та контейнери цієї інсталяції. Робота в них переривається.

## Резервна копія перед видаленням

- `full` — файли (`config`, `storage`) і БД (PostgreSQL, Redis); `db` — лише БД, без файлів; `none` — без копії.
- Копію створює штатний Backup Service цієї інсталяції (`python -m services.backup_service removal-snapshot` у його контейнері) у форматі `VERTEP-BACKUP-v1`, зашифровану поточним `config/backup.key`. Сервіс перевіряє checksum, розшифрування й склад: дамп PostgreSQL для обох варіантів, файлові джерела для `full`.
- Копія разом із `backup.key` (0600) переноситься в `/var/backups/vertep/<snapshot_id>/` (0700) поза installation root; checksum і ключ перечитуються вже з цього каталогу. Шлях друкується оператору.
- Якщо Backup Service не запущений, копію не створено або перевірка не пройшла, видалення не починається: не зупиняються служби, не ставиться marker, нічого не видаляється. `none` одразу виконує підтверджене видалення.

## Дані та спільне ПЗ

Після підтвердження видаляються також `config`, `tls`, `data`, `storage`, `models`, `logs`, `backups`, `.env`, `.update-backup.key` та неспільні Docker volumes інсталяції (зокрема volume БД). Колишній `--purge-data` приймається для сумісності, але нічого не змінює: видалення завжди повне. Підтверджуються каталоги даних, а не вміст кожного файла: служби, що працюють, змінюють дані (логи, черги) до зупинки, тому файли, записані після підтвердження, видаляються разом із каталогом. Повний перелік файлів із SHA256 — у `--dry-run` і журналі. Перетини зі сторонніми bind mounts і symlinks блокують операцію, symlinks у даних не обходяться. Volumes без мітки Compose або з використанням сторонніми контейнерами, спільні networks та images зберігаються; journal і recovery executor — теж.

Після видалення executor прибирає порожні каталоги даних, lock-файл update fence і сам installation root, якщо він став порожнім. Невідомий вміст не видаляється: його шляхи наводяться в `retained_unknown`, а результат — PARTIAL.

## Походження Docker images

Видаляються лише images, які до хоста приніс Vertep. Перший запис ownership inventory, зроблений bootstrap до першого pull і до створення будь-якого контейнера цього root, фіксує всі images, що вже були на хості (`image_provenance.preexisting`). Такі images — зокрема `postgres`, `redis`, `nginx`, prometheus чи grafana, завантажені оператором раніше — ніколи не видаляються, навіть коли їх використовували контейнери Vertep. Images, які використовує сторонній контейнер, також зберігаються.

Якщо inventory створено вже для працюючої інсталяції (старі версії без запису походження), походження невідоме. Тоді видаляються лише images, чий `repository@digest` збігається з підписаним `images.json` поточного чи збереженого release; решта зберігається з причиною у переліку.

Пакети Docker/Compose, драйвери, Toolkit, Ollama, apt repositories, Docker daemon settings, UFW/SSH зберігаються. Поточні інсталятори не мають повного журналу їхнього походження й попереднього стану; обґрунтувати автоматичне видалення або rollback цих змін неможливо. Опції обходу цієї перевірки немає. Їх видалення потребує окремих перевірених доказів і явного рішення оператора поза автоматичним executor.

## Належність та виконання

Compose project name `vertep` не є достатнім доказом. Перевіряються working directory/config files під потрібним root, resource inventory, перетини з усіма сторонніми контейнерами та фактичні посилання. Images видаляються без force; network/volume removal не обходить перевірку використання Docker. Global prune/autoremove не застосовуються.

Після підтвердження executor перевіряє перелік, зупиняє належні інсталяції системні тригери та виконавці оновлення, бере спільний з update/deployment OS lock і повторно звіряє перелік. Далі він створює admission marker, вимикає units, видаляє підтверджені контейнери й решту ресурсів, а в кінці видаляє код і CLI. Marker не дозволяє відновити dispatch паралельною зміною NORMAL. Невідомі файли не видаляються рекурсивно: непорожні software-каталоги залишаються й дають PARTIAL.

## Переривання та повторний запуск

Journal `state.json` і самодостатній `remove.py` зберігаються поза installation root у приватному каталозі `/var/lib/vertep-remove/<installation-and-plan-key>/`. Path виводиться після завершення або помилки; journal не містить значень secrets. Кожен завершений крок записується атомарно. При помилці результат FAILED, units не вмикаються назад і дані не домальовуються як видалені.

Поки CLI ще встановлений, `sudo vertep remove --resume --confirm <original-plan-sha256>` сам знаходить єдиний незавершений journal цього root у `/var/lib/vertep-remove`; кілька незавершених journals або їх відсутність — відмова без змін. Після видалення CLI оператор запускає **збережений** executor: `sudo python3 /var/lib/vertep-remove/<key>/remove.py --root <installation-root> --resume --confirm <original-plan-sha256>`. Він використовує підтверджений перелік із journal і не додає нових цілей. Повторне виконання пропускає завершені кроки; відсутність уже видаленого ресурсу не є помилкою. Новий installation ID або новий перелік отримує окремий journal. Після переривання marker зберігає maintenance до завершення операції.

## Результат

`SUCCEEDED` — інсталяцію видалено повністю. `PARTIAL` — команда друкує, що саме лишилося (невідомий вміст, який не видаляється рекурсивно), і шлях до журналу. `FAILED` — причина й збережений executor для продовження.

## Повторна інсталяція та відновлення

Після повного видалення root порожній або відсутній, volume БД видалено, тож bootstrap на тому самому root виконує чисту інсталяцію з майстром першого запуску: стара БД, дані, конфігурація, модулі й ownership inventory не підхоплюються. Поки `config/removal-in-progress.json` існує, видалення не завершене: bootstrap відмовляє до будь-яких змін і пропонує продовжити видалення. Після `PARTIAL` лишається лише перелічений невідомий вміст.

Старий стан повертається тільки явним відновленням копії ([backup/restore](backup-restore.md#копія-перед-видаленням-vertep-remove)): перед bootstrap покласти збережений `backup.key` у `<root>/config/backup.key` (0600), після інсталяції скопіювати `<snapshot_id>.vtbackup*` і `<snapshot_id>.json` у `<root>/backups/` і відновити snapshot в адмін-панелі.

Докази й межі перевірок — [приймання #446](acceptance/removal-446.md).
